# node-tuning：UV_THREADPOOL_SIZE 等 Node 运行时参数的验证

验证《Windows 原生 DSH 性能优化执行文档》步骤①「调 UV_THREADPOOL_SIZE 等 Node 参数」。

## 一句话结论

**对本机 DSH 无效，不建议启用。** 两个子项都不成立：

| 参数 | 文档预期 | 实测结果（DSH 真实场景） |
|---|---|---|
| `UV_THREADPOOL_SIZE=16` | 并发 fs 不再堵死、波动收窄 | **无收益，还略微变慢**（+7.8%，p=0.0018）。fs 仅占调用总耗时 **0.18%** |
| `--max-old-space-size=4096` | 提高堆上限 | **完全是 no-op**：本机默认已是 4288MB，指定 4096 得到同样的值 |

**但要区分清楚**：`UV_THREADPOOL_SIZE` 本身是有效的 —— 在**大文件并发读**场景下
TPS=16 真实提速 **20~29%**（见 §6）。只是 DSH 日常读的文件太小（几 KB），
单次 fs 只要 0.1~1.3ms，线程池根本来不及排队，所以在这个应用里用不上。

## 证据链

脚本按依赖顺序编号，全部支持重复运行。

### 1. 先证明测量能看见线程池效应（阳性对照）

```bash
node expK-pbkdf2.js
```

`crypto.pbkdf2` 确定由 libuv 线程池执行。实测：

| 任务数 | TPS=4 | TPS=16 | 加速比 | p |
|---|---|---|---|---|
| 4 | 91ms | 89ms | 1.03x | 0.39 |
| 8 | 182ms | 128ms | **1.43x** | 0.0051 |
| 16 | 437ms | 257ms | **1.70x** | 0.0051 |
| 32 | 944ms | 500ms | **1.89x** | 0.0051 |

→ **测量方法能看见线程池效应**。所以后面"fs 测不出差异"是真实结论，不是工具失灵。

### 2. fs 操作根本不构成瓶颈

```bash
node expO-final.js
```

| 项 | 实测 |
|---|---|
| fs 序列（stat + read 43KB） | p50 **0.90ms** |
| 真实 AOT 工具调用 | p50 **510ms** |
| fs 占比 | **0.176%** |

→ 即使 fs 变成**零成本**，工具调用也只能快 0.18%。这就是优化收益的理论天花板。

### 3. 各并发档位均无收益（FDR 校正）

```bash
node expI-saturation.js 20
```

N 个 fs 请求同时在飞，TPS=4 vs TPS=16：7 个档位（4/8/10/16/32/64/128）中**仅 N=4 一档显著，且方向相反**（TPS=16 慢 17.6%）—— 属于多重比较下的假阳性。

### 4. 真实项目目录 glob（最有利于该优化的场景）

```bash
node expP-realsd.js 30
```

253 个文件全部 stat，30 轮交错采样：

| 指标 | TPS=4 | TPS=16 | 差异 | p |
|---|---|---|---|---|
| p50 | 5.21ms | 5.13ms | -1.6% | 0.42 |
| stdev | 1.48ms | 1.39ms | -6.4% | 0.69 |

→ 连"波动收窄"这个最弱的预期也没能验证出来。

### 5. 真实调用链路端到端

```bash
node expH-real.js 30 10
```

AOT runner → cmd.exe，单次顺序 60 次 + 10 路并发 30 轮：全部无显著差异。

### 6. 修正：线程池本身有效，只是 DSH 用不上

```bash
node expQ-bigfile.js 15   # 64MB 大文件并发读
node expR-size.js 12      # 受益边界扫描
node expS2.js 40          # 真实项目文件，最终定论
```

**64MB 大文件并发读**（交错采样 15 轮）：

| 同时在读 | TPS=4 | TPS=16 | 差异 | p |
|---|---|---|---|---|
| 8 × 64MB | 143.4ms | 107.7ms | **-24.9%** | 0.061 |
| 16 × 64MB | 347.4ms | 270.0ms | **-22.3%** | 0.0008 |
| 32 × 64MB | 612.6ms | 487.8ms | **-20.4%** | 0.0012 |

→ 所以 libuv 线程池**确实**在管 fs，调大它**确实**能加速大文件并发读。

**受益边界扫描**（10 路并发）：

| 文件大小 | TPS=4 | TPS=16 | 变化 |
|---|---|---|---|
| 4KB | 1.04ms | 1.08ms | +2.9% |
| 128KB | 1.35ms | 1.29ms | -4.1% |
| 2MB | 4.08ms | 3.80ms | -6.6% |
| 8MB | 19.72ms | 17.59ms | -10.8% |
| 16MB | 39.92ms | 30.90ms | **-22.6%** |

→ 大约 **2MB 以上**才开始有像样的收益。

**最终定论**（真实项目 .cs 文件，stat→read 完整序列，10 路并发，40 轮交错）：

| 变体 | p50 | stdev | 相对 TPS=4 | p |
|---|---|---|---|---|
| TPS=4 | 1.336ms | 0.272ms | — | — |
| TPS=8 | 1.377ms | 0.277ms | +3.1% | 0.0020 * |
| TPS=16 | 1.441ms | 0.274ms | **+7.8%** | 0.0018 * |
| TPS=32 | 1.395ms | 0.262ms | +4.4% | 0.0001 * |

→ 在 DSH 真实的文件规模下，调大线程池**反而略慢**（多线程争抢同一把 NTFS 目录锁）。

## 为什么对 DSH 无效（机理）

1. **单次 fs 太快，线程池排不上队。** DSH 一次 `read_file` = 1 次 `stat` + 1 次 `read`，
   典型 .cs 文件 1~9KB，整条序列只要 1.3ms（10 路并发下）。
   默认 4 个线程在 1.3ms 内根本积压不起队列 —— 没有排队，加线程就没有收益。

2. **单次 fs 在工具调用里占比 0.18%。** 真实 AOT 工具调用 p50 = 510ms，
   fs 部分只有 0.90ms。即使 fs 变成零成本，端到端也只能快 0.18%。

3. **进程边界让线程池失效。** `UV_THREADPOOL_SIZE` 是进程内配置。
   DSH 的工具调用跑在主机进程里（`dsh-fs-local`），确实是同一个线程池；
   但并发峰值只有 10（`maxParallelToolCalls` 默认值），10 个在飞的请求
   在默认 4 线程下也只排 2.5 层，远没到"堵死"。

4. **小文件并发反而有害。** 多个线程同时 stat 同一目录会争抢 NTFS 目录锁，
   所以 TPS=16 比 TPS=4 慢 7.8%（p=0.0018）。

## 什么情况下这个措施才值得做

- 工作流里频繁读写 **>2MB** 的文件（日志、数据集、构建产物）
- 需要并发处理大量大文件（批处理脚本）
- 对 DSH 日常的代码阅读、glob/grep 搜索，**不建议启用**

## 复现方法

```bash
cd bench/node-tuning
# 生成测试数据
node -e "const fs=require('fs');fs.mkdirSync('files',{recursive:true});const b='const x=1;\n'.repeat(1000);for(let i=0;i<200;i++)fs.writeFileSync('files/f'+i+'.js',b)"
node -e "const fs=require('fs');fs.mkdirSync('tiny',{recursive:true});for(let i=0;i<4000;i++)fs.writeFileSync('tiny/t'+i+'.txt','x')"
# 依次运行
node expK-pbkdf2.js      # 阳性对照（必须先跑这个）
node expO-final.js       # fs 占比
node expS2.js 40         # 最终定论：真实文件
node expR-size.js 12     # 受益边界
node expP-realsd.js      # 真实 glob
```

## 方法论备注

本目录的脚本全部采用**交错采样**（每轮跑完所有变体）而非分组跑，避免机器负载漂移被误判成组间差异。统计用 Wilcoxon 符号秩检验（不假设正态），多重比较用 BH-FDR 校正。

中途修掉过一个自造的 bug：`normCdf` 直接传负 z 会算出 `p=1.5018` 这种不可能的值，已改为先取 `|z|`。

**一次自我纠错值得记录**：最初用小文件测出"无差异"，我错误地归因为
"Windows 文件 IO 走 IOCP 不走线程池"。后来用 64MB 大文件一测，
TPS=16 提速 22% —— 证明这个机理判断是错的。libuv 在 Windows 上
`uv_fs_read` 确实提交到线程池。真相是小文件太快、排不上队，
而不是线程池不管 fs。**如果没做这个反向验证，README 会留下一个错误的机理解释。**
