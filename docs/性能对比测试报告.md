> 测试时间：2026-11-02
> 环境：Windows / DSH 0.2.0-rc.2 / 你的 web 会话全程运行中（未中断、未改配置）
> 测试方法：独立 node 进程跑基准，**未安装插件、未改动任何 profile**

> ### 📌 关于本文数字的口径（2026-11-06 补注）
>
> 本文是**历史实测原始记录**，其中的具体数值（65.0% / 130~141ms / 59.1%~59.6% 等）
> 都是当时逐轮测出来的真实数据，**有意保留原样**，不做修改。
>
> 但后续独立复测给出了不同区间的结果（64.1%、66.6%、63.5%），

> 而不是某个具体数字。看数字请以 `npm run observe:report` 的多轮收敛结果为准。

## 一、先说结论

| 指标 | 结果 | 可信度 |
|---|---|---|
| **收益比例** | **65.0%**（可信轮次 64.8% / 65.0%） | 高 |
| **每次调用省时** | **约 130~141ms**（runner 开销 198~217ms → 69~76ms） | 高 |
| **p99 极端值** | node 331~393ms → AOT 173~220ms，**改善 131~206ms** | 高 |
| **失败率** | 120 次连续调用 **0 失败** | 高 |
| **内存增长** | 120 次后 RSS 52.6 → 54.7MB，**无明显增长** | 高 |

**结论：AOT runner 在当前 DSH 版本上收益显著且稳定，可以进入下一阶段。**

## 二、测量方法上的一件事

第一版跑出来是 40.5%，我曾据此判断「基准设计有缺陷」。**这个判断是错的** ——
基准本身已经是交错采样（每轮地板→node→AOT），设计没有问题。

真正的问题是**系统负载波动**。我在基准里加了：
- 每轮记录 CPU / 可用内存
- 输出 p99 / max 而不只是 p50/p95
- 用 IQR/中位数算离散度（不用标准差 —— 长尾会把标准差拉爆）
- **自动可信度判定**（离散度 >10% 直接标 UNRELIABLE）

这个判定机制立刻证明了价值：5 轮里有 3 轮被判为不可信。

## 三、第一层：隔离基准（5 轮 × 30 次）

| 轮次 | node p50 | AOT p50 | 收益 | 离散度(node/AOT) | 可信度 |
|---|---|---|---|---|---|
| 1 | 250ms | 109ms | 64.8% | 6.4% / 1.1% | FAIR |
| 2 | 279ms | 125ms | 63.4% | 16.4% / 15.1% | UNRELIABLE |
| 3 | 260ms | 124ms | 60.0% | 9.8% / 12.9% | UNRELIABLE |
| 4 | 238ms | 187ms | **24.8%** | 3.3% / **49.8%** | UNRELIABLE |
| 5 | 238ms | 109ms | 65.0% | 2.9% / 1.5% | GOOD |

**全部 5 轮中位数 63.4%，但范围 24.8%~65.0% —— 不能这么报。**

只看可信轮次：

| 轮次 | node p50 | AOT p50 | 收益 | runner 开销 |
|---|---|---|---|---|
| 1 | 250ms | 109ms | 64.8% | 217ms → 76ms（省 141ms）|
| 5 | 238ms | 109ms | 65.0% | 198ms → 69ms（省 129ms）|

**两轮高度一致（64.8% / 65.0%），这才是可报告的结论。**

### 第 4 轮为什么是 24.8%

AOT p50 从 109ms 跳到 187ms。我单独抓了一次分布：

```
按序: 122 109 109 109 110 109 111 109 94 109 111 109 110 111 110 110 111 111 110 191 111 174 127 127 110 112 143 127 111 110
排序: 94 109 109 109 109 109 109 109 110 110 110 110 110 110 110 111 111 111 111 111 111 111 112 122 127 127 127 143 174 191
```

分布呈**双峰**（≈110ms 和 ≈190ms 两簇），不是随机噪声 —— 是某个偶发因素
（杀软扫描、内存回收、其它进程）在干扰。这类干扰**无法从基准侧消除**，
只能通过记录 + 多轮取可信值来处理。

## 四、第二层：真实负载对照（3 轮 × 40 次）

| 轮次 | node p50 | AOT p50 | 收益 | node p99 | AOT p99 | p99 改善 | 失败 |
|---|---|---|---|---|---|---|---|
| 1 | 249ms | 109ms | 64.6% | 379ms | 173ms | **206ms** | 0 |
| 2 | 253ms | 109ms | 66.0% | 393ms | 220ms | **173ms** | 0 |
| 3 | 243ms | 109ms | 63.4% | 331ms | 200ms | **131ms** | 0 |

**关键发现：p99 和 max 全部改善，且改善幅度比 p50 更显著。**

这很重要 —— p50 好不代表体感好。交互式使用时，偶尔一次 400ms 的延迟
比平均快 130ms 更影响体验。AOT 不仅平均更快，**长尾也明显更短**。

## 六、这些数字意味着什么

按你日常使用估算（每次工具调用省 130ms）：

| 每天调用次数 | 每天省时 |
|---|---|
| 100 次 | 13 秒 |
| 500 次 | 65 秒 |
| 1000 次 | 2 分钟 |

**说实话：单看累计秒数，谈不上震撼。**真正的价值在于：

1. **长尾变短**：卡顿感来自 p99，而 p99 从 ~370ms 降到 ~180ms
2. **子代理/并行任务收益放大**：一次任务里如果有 20 个子进程，省 2.6 秒
3. **为更大的优化铺路**：runner 开销从 217ms 降到 76ms，剩下的 76ms 里
   还有优化空间（现在地板是 33ms，说明理论上还能再省 40ms+）

## 九、第三层：headless profile 实装验证

> 测试时间：2026-11-02
> 隔离方式：**独立 DSH_HOME**（`%TEMP%\dsh-tier3-test`），
> 你的 web / headless profile 全程未改动，测试后目录已删除。

### 做了什么

1. 建独立 DSH_HOME，装 `@boyingliu01/dsh-aot-runner`（`link:` 指向本仓库）
2. `dsh --dump-config` 确认插件条目被正确合并
3. 起真实 DSH 实例（5301 端口）
4. 用插件注入后**真实 spawn** 一次子进程，与 node runner 对照

### 结果

| 项目 | 结果 |
|---|---|
| 插件安装 | ✅ `pnpm add` 成功，链接到 `D:/projects/dsh-aot-runner/plugin` |
| 配置合并 | ✅ 显示 `patched by ...cordis.patch.yml` |
| DSH 启动 | ✅ 无告警 |
| 插件注入 | ✅ `runnerInvocation = ["D:/projects/dsh-aot-runner/dist/dsh-aot-runner.exe"]` |
| 真实 spawn | ✅ `exit=0`，`stdout="TIER3_OK"` |
| 与 node 一致 | ✅ 逐字节相同 |

### 过程中发现并修正的两个问题

#### 1. 配置覆盖方式写错了（文档缺陷，已修）

我最初在 profile 的 `cordis.patch.yml` 里写：

```yaml
- insert:
    - id: aot-runner
      name: '@boyingliu01/dsh-aot-runner'
      config: { enabled: true }
```

`--dump-config` 显示这会导致**同一个 id 出现两条**（包自带的 + 我插的），
因为 `insert` 是「新增一条」，不是「修改已有那条」。

正确的覆盖方式只需指定 id 和要改的字段：

```yaml
- id: aot-runner
  config:
    enabled: true
```

DSH 会显示 `patched by` 并正确合并。

**这是文档错误，不是插件缺陷** —— 但错的示例会让每个使用者都踩一遍，
已修正插件 README。

#### 2. `cmd.exe` 正斜杠绝对路径的固有怪癖（不是 runner 的问题）

验证过程中发现 `C:/Windows/System32/cmd.exe /c echo HELLO` 报
「The syntax of the command is incorrect」，而 `cmd.exe` 裸名正常。

一度怀疑是 runner 的参数处理 bug，直接绕过 runner 做原生对照：

```
cmd.exe                          → status=0  out="HELLO"
C:\Windows\System32\cmd.exe      → status=0  out="HELLO"
C:/Windows/System32/cmd.exe      → status=1  out=""  err="The syntax of the command is incorrect."
```

**确认是 cmd.exe 自身的固有行为**，与 runner 无关。
反斜杠绝对路径和裸名都正常，只有正斜杠绝对路径出问题。

记录在此，避免后来者（包括我自己）把它误判成 runner 缺陷再查一遍。

### 一个未验证到的点

想用 `dsh --profile headless "<任务>"` 跑完整的 LLM 任务链，但隔离 HOME 里
没有 API key（`MISSING_CREDENTIAL`）。这是隔离环境的预期结果 —— 它反而证明了
隔离是彻底的。

替代方案：直接驱动 `LocalSubprocessRuntime` + 插件，验证到 spawn 层。
**未覆盖**：LLM 决策链、多轮工具调用、子代理并发。这些留给实际使用观察。

## 十、生产路径实测（发现 DSH 注入缺陷后的补充验证）

### 起因

把插件装到真实 DSH 后**没有生效**，排查发现是 DSH 自身的缺陷，详见
[Issue #12](https://github.com/boyingliu01/dsh-aot-runner/issues/12)：
`spawn()` 调用 `launchWindowsJob(spec, env)` 时漏传第三个参数 `internals`，
导致所有基于 `internals` 的注入点失效。

为测出真实收益，在 `node_modules` 里临时补上这个参数（**1 行，语义等价于
上游修好后的样子**），然后重测。

### 补丁内容

```js
// lib/index.js:1368  before
launchLinuxScope(spec, env) : launchWindowsJob(spec, env)
// after
launchLinuxScope(spec, env, internals) : launchWindowsJob(spec, env, internals)
```

原始文件备份在 `/tmp/dsh-subprocess-local-index.js.bak`（md5 一致可校验）。

### 性能对比（3 轮，每轮 5×20=100 次，交替采样）

| 轮次 | node p50 | AOT p50 | 收益 | node 离散 | AOT 离散 | 失败 |
|---|---|---|---|---|---|---|
| 1 | 156ms | 63ms | **59.3%** | 11.7% | 1.9% | 0 |
| 2 | 156ms | 64ms | **59.1%** | 11.8% | 2.8% | 0 |
| 3 | 158ms | 64ms | **59.6%** | 20.5% | 4.1% | 0 |

**三轮收敛到 59.1%~59.6%，无失败、无输出不一致。**

p99 改善：107ms / 73ms / 124ms。

> 判定框显示 UNRELIABLE 是因为脚本以 **node 侧离散度 >10%** 为判据。
> 这正是两者的本质差异 —— **node runner 本身就不稳定（11.7%~20.5%），
> AOT 稳定在 2%~4%**。收窄 AOT 自身波动是设计目标之一。

### 真实命令（每项 15 次）

| 命令 | node p50 | AOT p50 | 每次省 |
|---|---|---|---|
| `hostname` | 156ms | 79ms | 77ms |
| `whoami` | 218ms | 63ms | **155ms** |
| `cmd /c echo` | 156ms | 63ms | 93ms |
| `cmd /c dir` | 156ms | 63ms | 93ms |

### 稳定性

| 轮次 | 调用数 | 失败 | 耗时 | RSS |
|---|---|---|---|---|
| 1 | 100 | 0 | 7.0s | 55→60MB |
| 2 | 300 | 0 | 21.5s | 58→61MB（有涨有落，非单调） |

### 熔断降级验证

注入一个损坏的 exe，连续调用 5 次：

```
第1次: 抛错 spawn UNKNOWN
第2次: 抛错 spawn UNKNOWN
第3次: 抛错 spawn UNKNOWN
第4次: exit=0 out="FB"     ← 已降级，恢复正常
第5次: exit=0 out="FB"
最终 invocation: undefined  （已恢复 node runner）
告警: [aot-runner] 熔断，降级到 node runner：Error: spawn UNKNOWN
```

**结论：最坏情况只影响 3 次调用**，第 4 次就自动恢复。

### 与第一、二层的差异

| 层 | 收益 | 说明 |
|---|---|---|
| 第一层（隔离基准） | 64.8% / 65.0% | 手工驱动 runner |
| 第二层（真实负载） | 63.4%~66.0% | 手工驱动 runner |
| **生产路径（本节）** | **59.1%~59.6%** | **走 DSH 真实 launchWindowsJob** |

生产路径略低（约 5 个百分点），因为多了 DSH 自身的 `bindManagedProcess`、
Job Object 分配、IPC 结果解析等开销 —— 这些两侧都要付，所以**绝对差值的
说服力比比例更强：每次稳定省 92~94ms**。

### 结论

在当前 DSH 版本上补上那一行后，收益**确定存在且可复现**：

- 比例稳定在 ~59%，绝对差值稳定在 ~92ms
- p99 改善 73~124ms（体感收益比均值更大）
- 300 次零失败，无内存增长
- 熔断器兜底，最坏影响 3 次调用

**值得给 DSH 提 issue 修复。**
