# 测量方法论：当工具比被测对象更容易出错

> 本文记录本项目在性能测量与测试可信度上踩过的坑。
>
> **写这篇的理由**：这个项目里最贵的两次误判，都不是代码写错了，
> 而是**测量工具的隐含假设错了**。第一次差点让我们放弃一个有效优化，
> 第二次差点让一个有缺陷的测试看起来是绿的。
>
> 这些教训与具体业务无关，值得沉淀。

---

## 摘要（只看这一节也能拿走的东西）

**核心结论：一次性能测量的误差，通常来自测量方式而不是被测对象。**

本项目曾用错误的测法得出「AOT 比 node 慢 20ms」，与自己基准的「快 68%」完全相反。
两个候选实现都在**错误的调用路径**上跑 —— 数字看起来很像真的，所以没人怀疑。

### 拿到任何性能数字，先问这 5 个问题

1. **我的调用方式，与被测系统的真实用法一致吗？**
   读它的调用契约（源码/README）再设计测法。这一步省下来的时间，
   通常不够抵一次错误结论的代价。
2. **两组对比的环境负载对等吗？**（负载差 >5% 的对比无效）
3. **这个差异大于测量噪声吗？** 组内重复测量的波动是多少？
4. **我是不是用「累计值」推出了「实时影响」？**
   （1451 秒累计 CPU ÷ 86400 秒 = 0.20% 系统算力，不是「严重瓶颈」）
5. **如果结论反过来说，数据还支持吗？** —— 做一次证伪尝试。

### 三个最容易犯的具体错误

| 错误 | 症状 | 正确做法 |
|---|---|---|
| **单调 A→B→A** | 看起来处理有效，实际是机器在变快 | **ABBA 交替**，让时间趋势对称抵消 |
| **用相对涨幅比较基准不同的量** | 基准小的那个显得「涨得更多」 | 比**绝对增量**或**尾抖**，不比百分比 |
| **把不可信的数字平均** | 得到一个「看起来很精确」的错误答案 | 标记 `UNRELIABLE`，宁可不给结论 |

### 一条元规则

> **当测量结果反复「不合理」时，把怀疑的顺序倒过来：**
> **先怀疑测量工具，再怀疑环境，最后才怀疑被测代码。**

最贵的误判成本结构总是三段式：
`以为代码有问题 → 查代码` → `以为环境有问题 → 查环境` → `发现测量假设错了 → 5 分钟修复`。

### 可直接复用的代码

本文配套的三态判定库：[`lib/bench-verdict.mjs`](../lib/bench-verdict.mjs) ——
**无项目耦合**，可整文件复制到任何 Node 项目：

```js
import { aggregate, VERDICT } from './lib/bench-verdict.mjs';
const v = aggregate(rounds);   // MEASURED | GAIN_CONSISTENT | UNRELIABLE
```

它的立场就是本文的立场：**宁可返回 UNRELIABLE，也不返回一个方向错误的确定结论。**

## 一、三个真实案例

### 案例 1：3609ms 的幽灵延迟

**现象**：早期用 `JsonSerializer` 做 AOT 序列化，测得启动耗时 **3609ms**，
而同功能的手写序列化只要 105ms —— 34 倍差距。结论似乎是"必须抛弃 JsonSerializer"。

**真相**：3609ms 是**测量伪迹**。真实值是 251ms。
差距确实存在（105 vs 251），但**量级完全错了**（不是 34×，是 2.4×）。

**根因**：测量时把 target 的 stdio 设成了 `'ignore'`。
在这个配置下，`Console.OpenStandardOutput()` 会**阻塞等待**一个永远不会
到来的写入端，这段时间被算进了"启动耗时"。

**怎么发现的**：严格同源 A/B —— 同样的源码、同样的编译参数，
**只改测量方式**（`'ignore'` vs 真实管道），数字从 3609 掉到 251。

**教训**：

> 当一个测量结果"好得不像真的"或"差得不像真的"，
> **先怀疑测量，再怀疑被测对象。**

---

### 案例 2：测试在 `test:all` 里偶发失败，单跑却总是通过

**现象**：零泄漏回归（100 次连续调用）单独跑 100% 通过，
放进 `npm run test:all` 串行执行时**偶发**失败，报"100 轮后仍有 runner 未退出"。

**第一次误判**：我以为是 runner 收尾慢，把固定 `sleep(500)` 改成轮询等待。
结果仍然失败——而且轮询了 9 次（8 秒）那个进程**还在**。

**第二次误判**：我怀疑是 `Get-CimInstance` 在高负载下漏报，
专门写了个对照实验跑 40 次……结果发现 CIM 和 `tasklist` 漏报的是**同一批 PID**。
说明问题在测试逻辑，不在查询工具。

**真相**：**基线竞态**。测试开头快照一次 `before = pidsByName(...)`，
但此刻**上一套件遗留的 runner 可能还在退出过程中**。
它们不在基线里，等被扫到时就成了"新增泄漏"。
单跑不复现，正因为前面没有别的套件。

**修复**：

```js
// 改前：上来就快照
const before = new Set(pidsByName('dsh-aot-runner.exe'));

// 改后：先等环境干净，再取基线；同时用精确 PID 追踪
let before = new Set();
await waitUntil(() => {
  before = new Set(pidsByName('dsh-aot-runner.exe'));
  return before.size === 0;
}, { timeoutMs: 20000 });

// 每轮记录自己启动的 PID —— 精确比对比「名字差集」可靠得多
const myPids = new Set();
// ...
if (h.state.pid) myPids.add(h.state.pid);
```

**教训**：

> **"按名字扫描 + 取差集"是最脆弱的泄漏检测方式。**
> 它依赖「环境在测试期间保持干净」这个隐含假设，而这个假设在
> 串行测试里根本不成立。**记录自己创建的 PID** 才是无歧义的判据。

### 案例 3：所有观测都"不可信"，但优化其实有效

**现象**：观测器写好了多轮采样 + 离散度筛选，但本机连跑 6 轮**全部**判为
`UNRELIABLE`。按字面理解，结论是"测不出来，不知道优化有没有用"。

**真相**：6 轮的收益比例是 **60.7 / 63.2 / 62.9 / 64.1 / 61.7 / 65.0%**
—— 跨度只有 4.3 个百分点。**优化显然有效，只是判据太窄。**

**根因**：本机常态负载 50~75%（杀软 `HipsDaemon` + 常驻办公软件），
绝对延迟噪声很大，单轮离散度**几乎不可能**压到 10% 以下。

**关键洞察**：

> 负载会**同时**抬高 node 和 AOT 的绝对延迟，但**比值保持稳定**。
> 所以「收益比例」对负载不敏感，而「绝对毫秒数」非常敏感。

**修复**：加第二层判据 `GAIN_CONSISTENT` —— ≥3 轮且收益跨度 ≤5pp 时，
**采信比例，绝对值仍返回 `null`**。

```js
// 绝不输出 netMs —— 那个绝对值确实被污染了
return {
  verdict: 'GAIN_CONSISTENT',
  gainPct: 64.1,
  netMs: null,      // ← 关键
  nodeP50: null,
  aotP50: null,
};
```

**教训**：

> 判据不可信时，**不是放宽阈值**，而是**换一个对噪声不敏感的指标**。
> 而且必须清楚划出"哪些数字可以用、哪些不能用"。

## 二、从这个项目提炼的 6 条规则

### 规则 1：先证明工具能看见东西

在断言"没有泄漏"之前，先故意制造一个泄漏，确认测试会失败。

```js
test('探针自校验：泄漏检查会失败', async () => {
  // 留一个活进程，assertAllGone 必须抛错
  const c = spawn('cmd.exe', ['/c', 'ping -n 30 127.0.0.1 > nul']);
  await assert.rejects(() => assertAllGone([c.pid], '自校验'));
});
```

**没有自校验的"全绿"没有意义** —— 它可能只是什么都没检查。

### 规则 2：拒绝给不可信的数一个漂亮的平均数

```js
if (!good.length) {
  return { verdict: 'UNRELIABLE', gainPct: null, netMs: null };
}
```

把 6 个"不可信"的数字平均一下，会得到一个看起来专业、实则无意义的结论。
**输出 `null` 比输出一个错误的数字更有价值。**

### 规则 3：差值比绝对值更稳

| 指标 | 对负载敏感度 | 用途 |
|---|---|---|
| 绝对延迟（p50/p95） | **高** | 只在环境干净时采信 |
| 收益比例 / 加速比 | **低** | 高负载下仍可用 |

判断优化是否有效时，**优先看比例**。

### 规则 4：警惕"未初始化状态"作为基线

案例 2 的本质是**基线在错误的时刻采集**。同类问题还有：

- 缓存未预热就测第一次请求
- 进程池未填满就测吞吐
- 文件系统缓存冷的时候测 IO

**先到稳态，再取基线。**

### 规则 5：测量工具本身会污染测量

`pidsByName` 每次调用都要起一个 PowerShell（约 300ms）。
100 轮回归里如果逐 PID 查询，测试会被拖到不可接受的长度——
而**这个开销本身**还会被算进被测代码的耗时里。

对策：批量查询、复用结果、把工具开销排除在计时区间外。

### 规则 6：一致性和正确性要分开验证

- **一致性**（A/B 逐字节相同）：`test/ab-verify.js`，28 项
- **性能**：`bench/`，独立测量
- **稳定性**：泄漏/竞态/混沌，7+5 项

**不要用一个测试同时验证这三件事** —— 它们需要的环境和判据完全不同。

## 三、反模式清单

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 只看绝对值不看比例 | 负载一波动就失真 | 优先看比例，绝对值标注环境 |
| 全部不可信时取平均 | 得到漂亮但虚假的结论 | 返回 `null` |
| 按名字扫描判断泄漏 | 依赖"环境干净"假设 | 记录自己创建的 PID |
| 固定 `sleep` 后断言 | 时序假设随机器变 | 轮询到条件满足或有上限 |
| 放宽阈值直到测试变绿 | 测试失去意义 | 换对噪声不敏感的指标 |
| 没有反向用例 | 测试可能什么都没检查 | 加自校验 |
| 单次测量就下结论 | 噪声可能主导 | 多轮 + 剔除异常 |

## 四、一条元规则

这个项目里两次最贵的误判，成本结构都是：

```
第一层误判：以为代码有问题  → 花时间查代码
第二层误判：以为环境有问题  → 花时间查环境
第三层才发现：测量假设错了  → 5 分钟修复
```

所以：

> **当测量结果反复"不合理"时，把怀疑的顺序倒过来：**
> **先怀疑测量工具，再怀疑环境，最后才怀疑被测代码。**

具体的自查问题：

1. 这个数字是**测出来的**，还是我**以为**测出来的？
2. 如果代码完全正确，这个测量会给出什么结果？
3. 如果代码有 bug，这个测量能发现吗？（**自校验**）
4. 这个结论**只在当前环境**成立吗？
5. 有没有可能是我**测量方式**造成的？

## 六、案例 6-7：从「代码结构推断」到「分段实测」

2026-11-07，在优化 Windows runner 时连续犯了两次同一类错误。
两个错误都由**同一种思维捷径**产生：看到代码结构就推断耗时归属，跳过测量。

### 案例 6：10ms 轮询

**推断**（错）：`PollLoop` 里 `Thread.Sleep(10)` 每轮固定睡满，
平均白付 5ms、最坏 10ms。改成 `WaitForSingleObject` 事件等待就能赚回。

**实测**（同环境交替对照，各 100 次）：

| | min | p50 | 分布（<5/<10/<20/≥20ms） |
|---|---|---|---|
| 改动前 | 2.8ms | 11.7ms | 15/27/18/40 |
| 改动后 | 3.2ms | 11.8ms | 14/28/19/39 |

**差异全在噪声内。** trace 揭示了原因：

```
[ 6ms] about to CreateProcessW
[29ms] CreateProcessW ok
[31ms] ResumeThread ok
[81ms] target exited code=0     ← 这 50ms 是 cmd.exe 自己的启动时间
```

原来那 10ms 睡眠被 target 自身启动时间**完全掩盖**了，不是可分离的延迟。

### 案例 7：解析热点

**推断**（错）：trace 显示 `[0ms] got message` → `[6ms] about to CreateProcessW`，
推断「解析 start 请求花了 6ms」，且 `AppendWide` 逐字符 `List<byte>.Add` 是热点。

**实测**（`npm run probe`，20~25 次采样，微秒精度）：

| 分段 | p50 |
|---|---|
| `json-peek-type` | 51µs |
| `json-parse-start` | 53µs |
| `build-cmdline` | 8µs |
| `resolve-exe` | 493µs |
| `env-block` | **41µs** |
| `resolve-stdio` | 239µs |
| **合计** | **0.89ms** |

六个分段加起来**占端到端 55.4ms 的 1.6%**。那 6ms 的真实归属是
`IMessageChannel.ReadMessage()` 读取 4.7KB IPC 消息 —— 数据必须从管道读进来，
**不可优化**。

### 可复用的做法

改内部实现之前，先回答「这个耗时真的在这个函数里吗」：

1. **建分段探针**（`bench/phase-probe.js` + `Trace.Measure(phase)`），微秒精度。
   毫秒精度的 trace 会把几百微秒的热点抹平成 0 或 1。
2. **算「未被分段的占比」**。本例中 98.4% 在进程创建 + target 启动上 ——
   这个数字一出来，就知道内部优化的天花板只有 1.6%。
3. **区分「可优化」与「不可优化」**：`ReadMessage` 读 4.7KB 不可优化；
   `resolve-exe` 遍历 PATH（~40 目录 × 3 扩展名）不可优化（语义必须与 libuv 一致）。
   **不是所有耗时都值得优化，有些是正确的成本。**
4. **A/B 对照要同环境交替**。单轮先后测会被负载漂移污染，本例前后差 0.1ms 属噪声。

## 七、案例 8：零覆盖不是「少测了点」，是「守卫失效了」

这里要说的不是「覆盖率数字低不好看」，而是**零覆盖会让守卫生效与否无人知晓**。

### 背景

`IpcChannel` 是与 DSH host 通信的唯一通道（fd 3），失败表现是「整个会话的子进程全部挂掉」。
它此前 **0/64 行覆盖** —— 不是遗漏，是构造它需要真实 fd 3，没人有办法在单测里造。

里面有一行专门处理「host detach」的守卫：

```csharp
// IpcChannel.cs，修复前
private static bool IsEndOfStream(uint got, int err) =>
    got == 0 || err == Native.ERROR_BROKEN_PIPE || err == Native.ERROR_NO_DATA;
```

### 建立的接缝

抽一个 `IChannelIo` 接口，把 `ReadFile` / `WriteFile` 换成可注入实现：

```csharp
internal interface IChannelIo
{
    (bool Ok, uint Got, int Error) Read(byte[] buffer);
    (bool Ok, uint Written, int Error) Write(byte[] buffer, int offset, int count);
}
```

生产路径只有 `Win32ChannelIo` 一个实现；测试里换成内存实现，就能精确炮制
「一次读返回多帧」「头被劈成两半」「中文被切在半个字符上」这些真实管道形态。

### 接缝一铺好，两个缺陷立刻现形

**缺陷 1：守门人认错了人。**
`ERROR_NO_DATA` 的实际值是 **232**，而 host detach 后管道真正返回的是
**233**（`ERROR_PIPE_NOT_CONNECTED`）。233 这个常量在 `Native.cs` 里**早就存在**，
只是从没被这行判断用过。原注释写「233」、常量定义「232」，两者矛盾却没人发现 ——
**因为没有任何测试会去检查「一个常量有没有被用到」。**

**缺陷 2（更隐蔽）：`ok` 参数被丢掉了。**
原签名只有 `(got, err)`，`ReadFile` 返回的 `ok` 没传进去。于是
「读失败 + got==0」被无条件当成 EOF —— `ACCESS_DENIED` 这类真错误
**被伪装成 host 主动断开**，通道坏了却没人知道。这条是写测试时才发现的：
我原先只打算测错误码映射，结果 `ReadMessage_未知错误码抛协议异常` 直接 FAIL 了。

### 结果

| 指标 | 改前 | 改后 |
|---|---|---|
| `IpcChannel` 覆盖率 | 0% (0/64) | **83.1% (64/77)** |
| 生产源码总覆盖率 | 39.9% | **45.4%** |
| C# 单测 | 142 | **166** |
| A/B 一致 | 28/28 | 28/28 |

### 可复用的做法

1. **「需要真实 OS 资源才能测」是接缝问题，不是不可测。** 把 P/Invoke 抽成接口，
   纯逻辑立刻可测。成本是一个接口 + 一个默认实现。
2. **零覆盖的代码里，缺陷不会报错，只会存在。** 上面两个缺陷都已存在很久，
   但 runner 一直「看起来能跑」—— 因为 detach 场景在正常测试里根本不发生。
3. **写测试时失败的那几条用例最有价值。** 本案例中 3 条 FAIL 全部指向真实缺陷，
   没有一条是「测试写错了」。先怀疑代码，再怀疑测试。

## 八、案例 9：覆盖率上不去的地方，往往藏着最贵的 bug

案例 8 讲的是「零覆盖让守卫失效」。这一轮把覆盖率从 39.9% 拉到 89.2%，
过程中又抓到两个**只在真实 OS 调用下才暴露**的缺陷 —— 而且第一个会让功能整体不可用。

### 突破：给「无法测试」的编排逻辑搭真实环境

`JobRunner` 有约 440 行 Win32 编排（CreateProcessW / Job 入队 / fd 描述符表 /
句柄继承 / 轮询收尾），之前只有 24.9% 覆盖。两条路都不通：

- **造 mock**：把每条 P/Invoke 换成假实现，测到的只是「mock 按我说的返回」，
  证明不了任何真实行为，反而制造虚假安全感
- **直接 new JobRunner 去 spawn**：**测试宿主进程直接崩溃**

崩溃的根因很有教育意义：CRT 的 `_get_osfhandle` 对**尚未分配**的 fd 会直接
`abort()` 进程 —— 这不是 .NET 异常，`try/catch` 和
`_set_invalid_parameter_handler` **都拦不住**。

正解是 `FdLayoutHost`：用 `CreatePipe` + `_open_osfhandle` + `_dup2`
在本进程里搭出与 host 一致的 fd 4/5/6(/7) 布局，并且**先把表撑到 7**，
让任何探测都落在「已分配但句柄无效」的槽位上，而不是未分配的洞里。

### 缺陷 1：空环境块让所有 spawn 失败

搭好环境后第一个用例就跑出 `CreateProcessW` 返回 `ERROR_INVALID_PARAMETER(87)`。
二分定位到 `BuildEnvironmentBlock`：

```csharp
// 修复前：空 env 时只产出 2 字节
bytes.Add(0);
bytes.Add(0);
return bytes.ToArray();
```

实测对比（同一个 fd 布局、同一条命令行）：

| 空 env 块大小 | CreateProcessW |
|---|---|
| 2 字节 | ❌ **err=87** |
| 4 字节 | ✅ 成功 |

也就是说 **host 一旦传空 env，每一次 spawn 都会失败**。

最刺眼的是：原有单测**已经存在**，断言「恰好 2 字节」，
而注释里写着「空 env 时若只产出 2 字节，CreateProcessW 返回
ERROR_INVALID_PARAMETER(87)」。

**注释和断言互相矛盾，而没有人发现 —— 因为没有任何测试真的调用 CreateProcessW。**

### 缺陷 2：未分配的 fd 让 runner 无声消失

host 若在 start 里声明 `control:"pipe"` 却没传 fd 7（host 侧契约违约），
runner 会去读 fd 7。修复前这会让 CRT `abort()` 整个进程 ——
host 只看到「子进程异常退出」，**连一条 EPROTOCOL 错误都收不到**。

修复不到位还有一个中间态：只装 invalid-parameter-handler 没用，
因为 CRT 默认走的是 `_invoke_watson`，绕过 .NET 的异常机制。
最终靠「测试与生产都预先占住 fd 槽位」解决。

### 结果

| 指标 | 本轮开始 | 现在 |
|---|---|---|
| 生产源码覆盖率 | 39.9% | **89.2%** |
| `JobRunner` | 19.0% | **86.2%** |
| `IpcChannel` | 0% | **83.1%** |
| C# 单测 | 142 | **254** |
| A/B 逐字节一致 | 28/28 | 28/28 |
| 覆盖率门槛 | 只报告不拦截 | **硬门槛 88%，未达标即中断构建** |

### 可复用的做法

1. **「测试宿主崩溃」是环境缺失的信号，不是不可测的证明。** 想清楚被测代码
   依赖哪套 OS 资源（这里是 fd 4/5/6），在测试里把那套资源造出来。
2. **CRT 的 abort 拦不住。** `_get_osfhandle` / `_dup2` 碰到未分配的 fd 会直接
   终止进程，`try/catch` 与 invalid-parameter-handler 都是无效的。
   对策是「先占位、再探测」。
3. **测试注释与断言矛盾时，几乎总是断言错了。** 本案例里注释写的是正确规格，
   断言写的是错误实现 —— 因为当初是照着实现写的测试。写测试时先问
   「规格要求什么」，而不是「当前代码返回什么」。
4. **覆盖率门槛要 ratchet。** 门槛取当前实测值向下取整，跑通后再逐步抬高；
   只升不降，防止新代码悄悄拉低整体。

## 九、案例 10：把覆盖率推到 100%，然后删掉 4 行代码

案例 9 结尾停在 89.2%。这一轮把它推到 **100.0%（1020/1020 行）**，
而最后 4 行不是靠「再补几个测试」消掉的 —— 是**删掉**的。

### 剩下的都在错误分支里

99% 之后剩下的一共 14 行，全部是失败路径：

| 位置 | 分支 | 真实触发条件 |
|---|---|---|
| `EJOBCREATE` | Job Object 创建失败 | 系统句柄耗尽 |
| `ENOENT` | CreateProcessW 抛异常 | 权限/资源问题 |
| `EPROTOCOL` | host 声明 control 却无 fd 7 | host 侧契约违约 |
| stdio WARNING | fd 4/5/6 缺失 | host 布局异常 |
| `EPOLL` | 轮询抛异常 | 句柄被外部破坏 |

这些在正常环境里几乎不可能自然发生。要覆盖它们，只有两条路：
伪造环境（脆弱、且验证的是伪造本身），或**给它们一个可注入的接缝**。

### 接缝的写法

统一成「默认真实实现，测试可替换」：

```csharp
internal Func<SafeJobHandle> CreateJob { get; set; } = SafeJobHandle.Create;
internal Action? PollHook { get; set; }        // null → 走真实 Poll
internal static Func<int, IntPtr>? ResolveControlHook { get; set; }
```

**默认值必须指向真实实现。** 中途我一度把它写成 `= (req, job) => { }`，
那会让生产路径静默不 spawn —— runner 起来了但 target 从未执行。
这个错误在代码评审时是最该盯的点：接缝的默认值决定了「忘记设置会怎样」。

### 最后 4 行的结论：那是死代码

推到 99.6% 后剩 4 行，逐条分析后确认**不可达**而非「难测」：

**① `if (req is null)` —— 被前置检查完全遮蔽**

```
HandleMessage: PeekType() 已保证「JSON 合法 + root 是对象 + type 是字符串」
ParseStart()  只在「JSON 非法」或「root 非对象」时返回 null
              → 两者都已被 PeekType 拦掉
```

**② `ProbeCandidates` 里的 `catch { }` —— .NET 8 上 File.Exists 不抛**

实测：非法字符（`?` `*`）、40000 字符超长路径、无权限路径，
`File.Exists` 一律只返回 `false`，不抛异常。
这个 `catch` 是 .NET Framework 时代的惯例残留。

两处都删掉了，并写明「为什么不需要它」。

### 为什么删比留好

保留一个永远进不去的分支，代价是：

1. **读者会以为还有一条错误路径要维护** —— 每次改这块都要重新推理一遍
2. **它会让覆盖率永远停在 99.x%** —— 而后人为了凑数会写 `#pragma`
   或伪造 `InternalsVisibleTo` 反射调用，把「不可达」掩盖成「已覆盖」
3. **真正的问题是为什么会有它** —— 层层前置校验已经保证过的条件，
   在下游重复判断，说明当初写的时候没想清楚职责边界

删掉之后代码更短、意图更清楚，覆盖率也就自然到 100%。

### 一路上的数字

| 阶段 | 生产覆盖率 | C# 单测 |
|---|---|---|
| 本轮开始 | 89.2% | 254 |
| 边界与失败路径 | 92.8% | 269 |
| 注入接缝 | 99.0% | ~310 |
| **删除死代码** | **100.0%** | **319** |

A/B 逐字节一致始终维持 28/28。

### 可复用的做法

1. **接缝默认值 = 生产实现。** 忘记设置时行为必须与未引入接缝时一致。
2. **难测 ≠ 不可达。** 先用注入验证「这段代码正确吗」，
   再用静态推理确认「这段代码还需要吗」—— 两件事顺序不能反。
3. **覆盖率上不去时，先怀疑设计。** 反复需要伪造环境才能测的代码，
   通常意味着职责切得不对；抽出纯逻辑后，剩下的薄壳往往可以直接删。
4. **100% 不是指标本身。** 这一路真正有价值的是途中发现的两个
   会让功能整体不可用的缺陷（案例 9），以及最后识别出的两段死代码。
   覆盖率只是让这两件事无处躲藏的手段。

## 八、案例 10：用相对涨幅比较两个基准不同的量，得出反向结论

**这是本文写作时最新的一次，也是最典型的一次 —— 它由本文作者自己犯下。**

### 背景

已知两组数据（`bench/load-matrix.cjs` 实测，CPU 37% / 76% / 100% 三档，
每档 n=20，测 `runner + bash` 完整生命周期）：

| CPU | node p50 | AOT p50 |
|---|---|---|
| 37% | 276ms | 114ms |
| 76% | 286ms | 126ms |
| 100% | 448ms | 257ms |

### 错误推理

看到「两边的 p50 都随负载上升」，于是算相对涨幅：

```
node:  (448 − 276) / 276 = +62%
AOT:   (257 − 114) / 114 = +125%
```

结论：「AOT 涨得比 node 还多，所以『AOT 延迟几乎不动』是假的，
AOT 的稳定性优势不存在。」

**这个结论是错的。**

### 错在哪

AOT 基准 114ms，node 基准 276ms，**相差 2.4 倍**。
负载升高时加进来的是**共享成本**（`bash` 自己也变慢，两边都要付），
而同样的绝对增量加在更小的基准上，**相对涨幅天然更大**。

这是分母造成的假象，不是稳定性差异。

### 换三个指标，结论完全不同

| 指标 | node | AOT | 正确读法 |
|---|---|---|---|
| 相对涨幅 | +62% | +125% | AOT 更差 ← **假象** |
| **绝对增量** | **+172ms** | **+143ms** | AOT 涨得更**少** |
| **净省**（node−AOT） | 162 → 160 → **191ms** | | 没塌，高负载下略增 |
| **尾抖**（p90−p50）@100% | **267ms** | **40ms** | AOT 少抖 227ms |

原始结论「AOT 更稳」是对的，指标用错了才被推翻。

### 可复用的做法

1. **比较两个基准不同的量，永远不要只看百分比。**
   先算绝对增量。若必须用比例，就固定分母（比如都除以 node 基线）。
2. **尾抖（p90−p50）比 p50 更适合衡量"稳定性"。**
   p50 随负载整体平移是正常的；真正影响体感的是尾部会不会炸。
3. **共享成本要单独识别。** 本例中 AOT 视角涨 143ms、node 视角涨 172ms，
   两者接近 —— 说明涨的主要是**共享的 target 成本**，不是某个 runner 退化。
4. **推翻自己之前的结论时，先问：是不是换了指标口径？**
   本例的"翻转"完全由指标选择造成，数据一点没变。

### 附带暴露的两个测法问题

`load-matrix.cjs` 本身有两处不符合本文规则，值得一并修：

- **没有 ABBA 交替**：每档内先跑完 20 次 node 再跑 20 次 AOT。
  负载漂移时两个 block 不可比。改法是交替采样。
- **没有地板扣除**：测的是 `runner + bash`，无法把「runner 差异」
  和「bash 成本」分开。所以上面的"共享成本"只能靠两个视角的增量接近来**推断**，
  而不是直接测出来。
