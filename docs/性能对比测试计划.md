> 状态：**待确认**

> （你升级 DSH + DSH 改了协议），当前不适用。真正的风险是
> **不能影响正在运行的 DSH 任务**。

## 一、先看一组实测数据（刚刚跑的）

在同一台机器、同一个会话、你的 DSH 正在运行时，连跑三次同一基准：

| 轮次 | node p50 | AOT p50 | 收益比例 |
|---|---|---|---|
| 第 1 次 | 340ms | 220ms | **40.5%** |
| 第 2 次 | 279ms | 124ms | **64.0%** |
| 第 3 次 | 369ms | 156ms | **65.6%** |

环境：CPU 负载 35%，可用内存 10.9GB。

**结论：波动幅度 25 个百分点。**单次测量完全不可信 ——
如果只看第 1 次，会得出「收益只有 40%」的错误结论。

这个问题必须先解决，否则后面所有对照测试都是白做。

---

## 二、核心矛盾

| 想要 | 冲突 |
|---|---|
| 真实环境的数据 | 真实环境有负载波动 |
| 稳定可信的数字 | 需要隔离，但隔离环境不等于真实环境 |

解法不是二选一，而是**分层测**：

```
第一层  隔离基准   独占机器片段，测「上限收益」——数字稳定，代表潜力
第二层  真实负载   你的 DSH 在跑时测 —— 数字波动，代表实际体感
```

两层的数字都记录，但**结论以第一层为准，第二层做交叉验证**。

---

## 三、对「不影响当前 DSH」的具体措施

这是你这次最关心的，我逐条列清楚。

### 3.1 性能测试本身的影响

| 措施 | 说明 |
|---|---|
| **不在你的 web 会话里跑** | 用独立的 node 进程跑 `bench/d1-ab-bench.js`，不碰 DSH |
| **限制并发与总量** | 默认 N=30，单轮约 30 秒；不跑 1000 次长跑 |
| **可随时中止** | 基准是前台进程，Ctrl-C 即停 |
| **不装插件** | 第一层、第二层都不需要给 profile 加依赖 |

实测：单轮 N=20 耗时 28 秒，CPU 占用很低（`user 0.154s / sys 0.185s`
—— 因为时间都花在等子进程启动上）。

### 3.2 如果要开插件（第三层）

只有确认前两层数据可靠后才做，且：

- **用 `headless` profile**，不动你正在用的 `web` profile
- 加依赖到 headless profile，web profile 完全不变
- 测完立刻移除

### 3.3 绝不做的操作

- ❌ 不给 `web` profile 加任何依赖
- ❌ 不重启你正在用的 DSH
- ❌ 不在你的会话目录里写入
- ❌ 不跑满 CPU 的长跑测试（除非你明确同意并挑时间）

## 四、测试方案

### 第一层：隔离基准（稳定数字）

**目标**：测出 AOT runner 的**上限收益**，数字要能重复。

**做法**：

1. **交替测量，消除漂移**
   现在的做法是「先跑 30 次 node，再跑 30 次 AOT」——
   如果这期间系统负载变了，差异会被算进结果。
   改成 **A/B/A/B 交替**：node、AOT、node、AOT… 各 30 次。
   这样任何负载漂移对两边影响相同。

2. **记录环境指标**
   每轮记录 CPU 负载、可用内存，事后判断某轮是否异常。

3. **跑多轮取中位数**
   连跑 5 轮，每轮内部交替；取 5 轮的 p50 中位数。
   丢弃明显异常轮（负载 > 60% 时测的）。

4. **同时测「地板块」**
   继续保留 `hostname.exe` 直连作为地板，
   用来区分「runner 开销」和「系统本身变慢」。

**交付物**：一份稳定的收益数字 + 波动范围（如 64.1% ± 1.2%）。

**判据**：
- 5 轮 p50 的离散度 < 5% → 数据可信
- 离散度 > 10% → 系统干扰太大，需要挑空闲时段重测

### 第二层：真实负载对照（体感验证）

**目标**：在你的 DSH 正常工作时，确认 AOT 不会掉链子。

**做法**：

- 不装插件，只用基准脚本在真实负载下跑几轮
- 重点不是数字，是**失败率**和**极端值（p99/max）**
- 观察：有没有超时、有没有失败、有没有异常慢的调用

**判据**：
- 失败率 = 0
- p99 不超过 node 版本的 p99

### 第三层（可选，需你同意）：headless profile 试用

**目标**：验证插件本身在真实 DSH 里工作正常。

如果你觉得有必要，我可以：

1. 在 `headless` profile 里装插件
2. 起一个 headless DSH 会话
3. 跑几个任务，观察日志
4. 测完移除

**这一层完全不碰你的 web 会话。**

## 五、需要你确认的点

### Q1：什么时候做「隔离基准」？

隔离基准需要相对空闲的机器约 3~5 分钟（5 轮 × 30 秒 + 间隙）。

- A. 现在就做（接受负载波动，我事后标注哪些轮次不可信）
- B. 你挑个空闲时间告诉我，我那时跑
- C. 只用后台低优先级跑，不催你

**我建议 A**：现在先跑一版，看离散度如何；如果太大，再约时间。

### Q2：要不要做第三层（headless 试用）？

- 要 —— 能验证插件真的能用，但要额外做安装/移除步骤
- 不要 —— 只做前两层，插件留到你真正要用时再开

**我建议先做前两层**，第三层等你看完数据再决定。

### Q3：测多长时间？

- 快速版：5 轮 × 30 秒 ≈ 4 分钟
- 充分版：10 轮 + 多次重复 ≈ 10 分钟

**我建议快速版**，先拿到数字再说。

## 六、我接下来要改的代码

### 6.1 基准脚本改造（`bench/d1-ab-bench.js`）

现状问题：

```js
// 先全跑 node，再全跑 AOT —— 负载漂移会污染结果
await measure('node', N);
await measure('aot', N);
```

改成：

```js
// 交替：每轮各跑一次，把漂移均摊到两边
for (let i = 0; i < rounds; i++) {
  nodeSamples.push(await oneCall('node'));
  aotSamples.push(await oneCall('aot'));
}
```

同时增加：

- 每轮记录 CPU/内存
- 输出 max/p99，不只是 p50/p95
- 输出离散度指标，自己判断数据可不可信

### 6.2 新增 `bench/perf-report.js`

把多轮结果汇总成一张表，算出：
- 各轮 p50 的中位数
- 离散度
- 建议结论（数据可信 / 需重测）

## 七、我会诚实处理的两件事

1. **如果数据离散度大，我会直接说「这批数据不可信」**，
   而不是挑一个好看的数字汇报。

2. **如果 AOT 在真实负载下出现 p99 退化**，我会指出来 ——
   平均值好不代表体感好，偶发的慢调用对交互式使用影响更大。
