# 我的基准测试说我的代码慢了 20ms。错的是基准测试。这样的事发生了五次。

> 这是一篇**发布稿**，面向掘金 / V2EX / 知乎等技术社区。
> 配套的完整长文（含 8 个案例、6 条规则、可复用代码）见
> [`docs/测量方法论-当工具比被测对象更容易出错.md`](../测量方法论-当工具比被测对象更容易出错.md)。
>
> **状态**：已发布（2026-11-27）→ [掘金](https://juejin.cn/post/7712783109374869558)

---

我写了一个 Windows 原生替代品，用来替换 DSH（一个 AI 编程助手的宿主）里的
Node.js 子进程启动器。理论上它能省掉每次起子进程时重新加载 Node 运行时的开销。

写完第一版，我做了一次基准测试。结果是：**我的实现比原来的慢 20ms。**

我差点删掉整个项目。

最后发现：**错的是基准测试。**

而这件事，在我做这个项目的三个多星期里，发生了**五次**。五次都是同一类错误：
**测量工具本身错了，但数字看起来很像真的。**

这篇文章讲这五次，以及我从里面提炼出的几条规则。如果你做性能优化，
这些坑你大概率也会踩，只是不一定知道。

---

## 第 0 次：那个 20ms 的"反向结论"

我第一次测的时候，只想要一个粗糙的对比，于是写了个十行脚本：

```js
const t0 = performance.now();
spawn(runnerPath, ['--', ...argv], { stdio: 'ignore' });  // ← 这里
```

测出来：AOT 版慢 20ms。

问题在 `stdio: 'ignore'`。真实的调用契约要求 `stdio[3] = 'ipc'`，
runner 要在这条 IPC 通道上和宿主握手、收发控制消息、报告子进程的退出码。
我把 `stdio` 设成 `ignore` 之后，两个候选实现都从"协议入口"跑到了"立刻失败退出"。

**两个都在错误的路径上跑 —— 所以那个 20ms 测的不是性能，是两个错误路径之间的差。**

而真实契约下，AOT 版快了 68%。

> **规则 1：测之前先读被测物的调用契约。**
> 调用方式错，测出来的数字与真实性能**没有关系**，而且是"看起来很像真的"那种错。

这个教训后来被我写进了基准脚本的开头，占了三行注释。
每次有人（包括未来的我）想"简化一下"那个 `stdio`，都会先读到它。

---

## 第 1 次：写一个更轻的基线，等于低估自己的收益

发现调用契约错了之后，我改用了真实的 stdio 布局。但基线还是我自己写的：

```js
// "用 node 跑同样的东西" —— 看起来等价
const baseline = () => spawn('node', ['-e', 'console.log(1)']);
```

结果：AOT 只省了 9%。

换成 DSH 真实的 `runner.js` 之后：**省了 68%。**

原因很简单：`node -e 'console.log(1)'` 比 `runner.js` 轻得多。
它不做 IPC 握手、不解析模块、不建控制通道。**我拿一个轻量的东西当基线，
当然测不出"替换掉一个重的东西"的收益。**

> **规则 2：用被测系统自带的基准工具，别自己写简化基线。**
> 自写的基线总是比真实实现轻 —— 而且轻的部分恰好是被优化的那部分。

---

## 第 2 次：用累计 CPU 秒数判断"严重瓶颈"

这个不是我的项目，是我在排查自己电脑为什么常年 90% CPU。

我用 `Get-Process` 看累计 CPU 时间，发现某个输入法升级程序的累计 CPU 是 **1451 秒**。
看起来是巨兽。

但换个算法：`1451 秒 ÷ 86400 秒 ≈ 0.017 核 = 0.20% 系统算力`。

实时采样确认：它真的只占 0.20%。

**"累计 1451 秒"和"现在正在拖慢你"是两件不同的事。** 前者是历史总量，
后者是当前占用率。我把前者读成了后者。

> **规则 3：用实时占用率判断影响，不用累计值。**

---

## 第 3 次：单调变化的序列，看起来像"处理有效"

性能测试最常见的自我欺骗是 A-B-A：先测基线，再测优化，再测一次基线。

如果结果是 `A1 = 高`、`B = 中`、`A2 = 低`，人会本能地读成"B 比 A1 好"。
但**A2 比 B 还低**这件事说明：真正在动的是"时间"，不是"处理"。
后台任务结束了、缓存热了、CPU 降频恢复了 —— 任何一个都能造成这种单调漂移。

本项目踩得更隐蔽：在**负载矩阵**实验里，把同一档位内的顺序写成
「先跑完 20 次 node，再跑 20 次 AOT」。在每一档内部，"时间"与"实现"是**共线**的 ——
晚跑的那一组永远占便宜（或者永远吃亏），你无法从数据里把两者分开。

所以本项目现在的规矩是 **ABBA 交替**：`A, B, B, A`，让时间趋势对称抵消。
README 里每个性能数字都标注了采样方式（"ABBA 各一轮共四轮 × 25 次"），
就是为了让人能判断"这个数字有没有抵消掉趋势"。

即便如此，**ABBA 也不能拯救一切**。有一次 ABBA 实验里两组负载差了 10 个百分点、
差异方向还和负载相反 —— 那次的正确结论是"**本轮不可比**"，
而不是"挑出其中一组更快"。

> **规则 4：A-B-A 不够，要 ABBA 交替；同时记录每轮负载，负载差 >5% 的对比直接作废。**

## 第 4 次：高负载下，所有结论都被噪声吞掉

我想验证"AOT 在系统高负载时是否更稳"。跑了三次：

| 重复 | node 离散度 | AOT 离散度 | 谁更稳 |
|---|---|---|---|
| 第 1 次 | 59.6% | 15.6% | AOT |
| 第 2 次 | 38.4% | 63.5% | **node** |
| 第 3 次 | 13.0% | 6.3% | AOT |

**方向翻转了一次。**

如果我只跑一次（而且是第一次），我会自信地宣布"AOT 在高负载下离散度显著更低"。
但三次里有一次方向相反，说明**这个指标本身在高负载下的重复性就不足以支撑任何结论**。

后来我在同一台机器上做了回归，发现**负载几乎解释了全部方差**，
其余所有"优化因素"加起来只占很小一部分 —— 也就是说，
高负载下测到的差异，绝大部分其实只是在测"当时的机器有多忙"。
（这类回归的绝对系数在不同机器上不可移植，所以这里有意不给具体数字：
给了反而会诱使别人拿它去套自己的环境。方法论长文里记了完整的判定过程。）

> **规则 5：先等负载降下来再测，并且必须报告负载。负载差 >5% 的对比无效。**

## 第 5 次：门禁"跑起来了"，但什么都没检查到

这一条最阴险，因为它**往好的方向说谎**。

我给发布流程加了一道检查：如果 npm 上没发出新版本，就失败。
但代码里有个判断写错了方向 —— `permissions.id-token: write` 常开让
OIDC 判断恒为真，于是"Trusted Publisher 没配"这种情况走到了
"没有 NPM_TOKEN" 分支，然后 `exit 0`。

结果：**job 全绿、GitHub Release 成功、npm 上什么都没有、零失败信号。**

那道检查确实"跑了"。它只是**没检查到任何东西**。

同一时期我还遇到三次同类：

1. 门禁说"找不到契约文件"，真实原因是**少一个环境变量**，异常被吞了 ——
   错误信息指向的方向与真实原因**无关**。
2. 我判断"某个门禁不读某文件"，依据是**从别的实现反推**。
   真实判据在那个门禁自己的源码里，它确实读。删掉后门禁立刻拦住了提交。
3. 我写了断言"步骤 A 必须在步骤 B 之前"，断言通过、CI 也绿 ——
   但 A 产出的路径，B 根本看不见。**顺序对了，路径没通。**

> **规则 6：结构断言证明不了连通性。**
> "谁在谁之前"是必要条件，不是充分条件。要验证"A 找得到 B"，就得真的让 A 去找 B。

这条规则后来变成了一个具体实践：**每次新增检查，都要故意改坏被测对象，确认它会红。**
改不红，说明那条检查是空的。

## 一条元规则

上面六条规则如果只能记一条，记这个：

> **当测量结果反复"不合理"时，把怀疑的顺序倒过来：
> 先怀疑测量工具，再怀疑环境，最后才怀疑被测代码。**

我这两次误判的成本结构都一模一样：
`以为代码有问题 → 查代码` → `以为环境有问题 → 查环境` → `发现测量假设错了 → 5 分钟修复`。

最贵的那一段，永远是"查代码"和"查环境"。

---

## 这些规则的代价

说实话，"宁可说测不出来"是有代价的：

- 你没法在周报里写"AOT 在高负载下更稳"，虽然那听起来很好
- 你得承认自己跑了三次还是没结论
- 你的基准报告里会出现 `UNRELIABLE` 这个词，看起来很不专业

但我见过更糟的：**一个方向错误的确定结论，会让整个团队基于错误前提做决策。**

在我这个项目里，如果我在第 0 次那个 20ms 就认了，
我会删掉一个实际快 68% 的实现 —— 因为它"没用"。

> **错误结论比没有结论更糟。**

## 关于那个项目的进展（诚实说明）

如果你是因为性能话题来的，顺便说一下它的现状 —— **它还没真正用起来。**

核心功能做好了、性能验证了、发布链路打通了，但它依赖 DSH 里的一个上游缺陷修复：
DSH 调用两个 `launch*` 函数时漏传了一个参数，导致所有注入被静默忽略。

我在 [discussion #11893](https://github.com/deepseek-ai/deepseek-harness/discussions/11893)
里报了 24 天（2026-11-02 至今），上游在 0.2.2-rc.5 / 0.2.3-alpha.1 / 0.2.3-alpha.2 三个版本里都没修 ——
而且那行代码**连行号都是 1574，三个版本完全相同**。

有意思的是：上游在重构时**保留了这个参数、保留了局部变量，就是没往下传**。
这说明不是"忘了加"，而是**那条代码路径没被测试覆盖到** ——
这恰好又是本文主题的另一个侧面。

所以这个项目现在有一个一行补丁（改一个文件、插入一处实参、可一键还原），
以及一套完整的验证：见 [vendor/README.md](../../vendor/README.md)。

**如果你也用 DSH**，去那个 discussion 里说一声"我也需要这个修复"，
比在我的仓库点 star 有用得多。
