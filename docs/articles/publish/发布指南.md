## 为什么我不能替你发

我有文件系统访问权，但**没有任何平台的登录凭据**（掘金/V2EX/知乎都用浏览器
Cookie 或扫码登录，不在我可访问的范围内），也**没有浏览器自动化能力**。

更根本的原因是：发布是**在你的账号下、以你的名义**产生公开内容，
这个署名动作应该由你确认。我可以把材料准备到「只需粘贴 + 点发布」的程度，
但最后那一下应该你来按。

> 顺带说明：掘金和知乎对自动化发帖的风控很严，脚本发帖有封号风险。
> 手动发布在这里不是妥协，是正确做法。

## 一、掘金发布（推荐首发）

### 1. 复制正文

打开 [`掘金版.md`](掘金版.md)，**全文复制**。

这个版本已经做过三处针对掘金的处理（相对原稿）：

| 处理 | 原因 |
|---|---|
| 4 个相对链接改成**绝对 URL** | 掘金会剥掉相对路径，原稿里 `../测量方法论...` 全部会变成死链 |
| 删掉开头「这是一篇发布稿」的元信息块 | 那是给仓库读者看的，对外发布是噪音 |
| 保留全部 5 张表格 + 3 个代码块 | 掘金对这两者渲染良好 |

### 2. 标题

推荐（已用作文件名和封面）：

```
我的基准测试说我的代码慢了 20ms。错的是基准测试。这样的事发生了五次。
```

备选：
- `我踩了 6 次同一个坑：测量工具本身在骗你`
- `宁可说"测不出来"：一次性能优化的 6 次自我欺骗`

> 掘金标题建议 20~40 字，上面三个都在范围内。
> **第一个最优**：有具体数字、有反转、有"五次"这个具体量。

### 3. 封面图

上传 [`cover-1200x630.png`](cover-1200x630.png)。
内容：深色底 + 红色标题「我的基准测试说 / 我的代码慢了 20ms / 错的是基准测试」
+ 左下核心对比（`基准测试：慢 20ms` 红色 / `真实契约：快 68%` 绿色）
+ 右侧「同一类错误，发生了 5 次」的点阵。

### 4. 分类与标签

| 项 | 建议 |
|---|---|
| 分类 | **性能优化**（若没有，选「后端」或「程序员」）|
| 标签 | `性能优化` `基准测试` `测试` `方法论` `踩坑` |

> 标签宁少勿多，掘金最多 5 个。前两个最重要（决定初始推荐池）。

### 5. 摘要（掘金要求填，120 字内）

```
我的基准测试说我的代码慢了 20ms，我差点删掉项目——错的是基准测试。
五个真实案例：错误的调用契约、过轻的基线、累计 CPU 秒数、单调 A-B-A、
以及"门禁跑了却什么都没检查到"。附一条元规则和一个可直接用的判定库。
```

## 二、发布后的动作（按重要性）

### 立刻做（前 10 分钟）

- [ ] **自己先读一遍渲染效果** —— 重点看那 5 张表格有没有错行
- [ ] 确认 4 个外链可点（都在文末「可以直接用的东西」和「诚实说明」两节）
- [x] 把文章链接回填到（2026-11-27 用 `scripts/backfill-article-links.mjs` 完成）：
  - [x] README 顶部「先读哪一篇」表
  - [x] `docs/测量方法论-当工具比被测对象更容易出错.md` 开头
  - [x] 本文档 §四「已发布链接」
  - [x] 另加：`CHANGELOG.md`「未发布」段、仓库原稿的状态行

> 回填用的是脚本，不是手改：`node scripts/backfill-article-links.mjs --url <URL>`。
> 手改容易漏（尤其仓库原稿里那行「状态：待发布」），而漏了之后读者看到的还是「待发布」。
> 校验：`node scripts/backfill-article-links.mjs --check` 应输出「✅ 长文链接已回填」。

### 当天做

- [ ] **回复每一条评论** —— 掘金的推荐算法对"发布后 2 小时内的互动"权重很高
- [ ] 如果有人在评论区问「DSH 是什么」，直接给 discussion #11893 的链接

### 不要做

- ❌ 不要自己点赞/刷数据（会被识别，且破坏文章唯一的资产：可信度）
- ❌ 不要发到多个平台时用完全相同的标题（会被判重复内容，压权重）
- ❌ 不要在评论区与人争论 DSH 好不好（那会带偏话题）

## 三、英文版（`English.md`）

**不是直译，是重写。** 差异：

| 项 | 中文版 | 英文版 |
|---|---|---|
| 语气 | 直接、短句、段落紧凑 | 更平、更少感叹、段落稍长 |
| 案例顺序 | 相同 | 相同（保持事实一致） |
| 本地化表达 | 「宁可说测不出来」 | `return UNRELIABLE rather than a confidently wrong answer` |
| 章节标题 | 第 0 次 / 第 1 次… | Case 0 / Case 1… |

**事实已交叉核对一致**（20ms、68%、1451、59.6%/38.4%/13.0%、
15.6%/63.5%/6.3%、1574、24 天）。

发布渠道建议（按匹配度）：

| 渠道 | 说明 |
|---|---|
| **dev.to** | 门槛最低，Markdown 直接贴，有稳定技术读者 |
| **Hacker News**（`Show HN` 或直接 submit） | 受众最大，但对营销腔极敏感 —— 当前文案可以，别加任何推广语 |
| **r/programming** | 需要账号有一定 karma；标题不要带感叹号 |

> ⚠️ HN 的正确姿势：**标题就用第一句**，正文不要贴全文（贴链接），
> 然后自己在首条评论里补充背景。正文贴全文在 HN 会被当作自我推广降权。

## 五、如果效果不达预期

先别改文章。按顺序查这三件事：

1. **是不是根本没进推荐池？** 掘金发布后 2 小时内的阅读量若 < 50，
   基本可判定没进池子 —— 通常是标题太平或标签不匹配，**可以修改标题重发一次**。
2. **是不是读者到不了仓库？** 看 GitHub 的 `traffic/popular/referrers`，
   如果掘金没出现在 referrer 里，说明文章里的链接没人点 ——
   那就要在文中段（而不是文末）加一个更显眼的仓库链接。
3. **是不是仓库转化不了？** 看 `traffic/views` 涨了但 star 没涨 ——
   这才是仓库首页的问题（README 前 30 秒没讲清价值）。

> 这三步对应漏斗的三个环节：**曝光 → 点击 → 转化**。
> 不要一上来就改文章；先确认断在哪一环。
