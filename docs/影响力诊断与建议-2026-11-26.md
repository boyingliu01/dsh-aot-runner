## 一、先看数据：真实的漏斗断在哪一环

### 1.1 六个数字（2026-11-26 实测）

| 指标 | 数值 | 说明 |
|---|---|---|
| ⭐ Stars | **0** | 仓库创建 26 天 |
| Forks | **0** | |
| Watchers / 订阅 | **0** | |
| GitHub 浏览（14 天） | **11 次 / 11 独立访客** | 平均每天 < 1 人 |
| Git 克隆（14 天） | **393 次 / 132 独立** | 峰值 89/天 |
| npm 下载（30 天） | **1336 次** | 峰值 313（首发日）|
| Release 资产下载 | 每个资产 **1~2 次** | 7 个 Release 全部如此 |

### 1.2 漏斗的断点非常明确

把上面的数换成比值，问题一眼可见：

```
npm 下载 1336  ┃ GitHub 浏览 11        →  121 : 1
Git 克隆  393  ┃ GitHub 浏览 11        →   36 : 1
GitHub 浏览 11 ┃ Star        0        →    0 : 1
```

**三个结论，按重要性排序：**

#### 结论 A：下载量不是「用户」，是机器

- npm 日均下载 1336/30 ≈ 45 次，但**逐日曲线**暴露了真相：

  | 日期 | 11-06 | 11-07~08 | 11-09 | 11-10~11 | 11-12 起 |
  |---|---|---|---|---|---|
  | 下载 | 313（首发）| 115 / 197 | 21 | 167 / 176 | 持续 15~42 |

  首发日 313、随后 6 天高位、**11-12 之后长期稳定在 15~36/天**。

- 而同期 GitHub 浏览是 **11 次 / 14 天**。
  **没有任何一个真人会因为「看到项目」而每天安装 20 次。**

- 克隆 393 次 / 11 次浏览 = **36:1**，同样是机器特征
  （镜像、CI、依赖扫描、自动抓取）。

> **所以：npm 的 1336 和克隆的 393 不能当作用户数。**
> 真实的、可归因的人类接触量是 **11 次浏览**。
> 这个数字才是需要提升的那个 —— 不是下载量。

#### 结论 B：漏斗断在「发现」，不在「质量」

浏览 11 次、star 0。这两个数字放在一起，**不能推出「东西不好所以没人赞」** ——
11 个访客里 0 个点赞，在统计上完全说明不了质量（样本太小）。

能推出的是：**根本没人到达这个页面。** 121:1 的下载/浏览比意味着
分发渠道（npm、镜像）已经在跑，但**发现渠道（搜索、社区、话题）是空的**。

#### 结论 C：Release 资产 1~2 次下载，说明「预编译二进制」这条路没被用到

7 个 Release、每个资产 1~2 次下载 —— 基本等于「作者自己下载测试」。
这与「npm 包内自带 exe」的事实一致：**能走到 Release 页面的人本身就不存在。**

## 二、为什么现在这样（不是自我批评，是定位问题）

### 2.1 三个结构性障碍

| 障碍 | 事实 | 影响 |
|---|---|---|
| **① 上游缺陷未修**（但**已有第三方修复分支**，见 §2.3） | discussion #11893 / #12532 开了 24 天；master 截至 2026-11-26 仍**未修** | 装完**默认不生效**，需要打补丁。这是最致命的转化障碍 |
| **② 目标用户池极小** | DSH 本身是新兴项目；用 DSH + 用子进程 + 在乎 100ms + 用 Windows x64 的交集 ≪ DSH 用户数 | 就算曝光到位，可转化人群也少 |
| **③ 语言墙** | README 全中文；GitHub 的主要流量语言是英文 | 英文用户进来直接退出 |

**特别注意 ② 的一个反直觉之处**：
「性能优化插件」的受众天然比「功能插件」小一个量级。
性能优化的价值主张是「省 100ms」——而人对 100ms 的感知阈值远高于此，
**只有高频调用子进程的重度用户才会觉得值**。这不是产品缺陷，是市场大小。

### 2.3 【2026-11-26 新发现】上游已有第三方修复分支 —— 这是目前最大的机会

查证 discussion 评论区时发现了一个**此前没有跟进的关键进展**：

**① 存在一个重复议题 #12532，早于我们的 #11893 两分钟创建**
（`2026-11-07T06:04:43Z` vs `06:06:58Z`），两者互相引用。

**② 有第三方贡献者（`aturzone`）独立确认了同一根因，并写了修复**
（`2026-11-07T11:24:00Z` 评论）：

> 分析成立，已按同一处修复（`LocalSubprocessRuntime.internals` 的 runner seam
> 现在会真正进入生产 launch 路径）
> 分支：`aturzone/deepseek-harness:fix/subprocess-managed-internals`
> commit `ab42e3b983`

该 commit 的说明写得很清楚，而且**直接引用了这两个 discussion**：

> `LocalSubprocessRuntime.internals` is the documented test seam, but `spawn()`
> forwarded it only to the fallback `spawnSubprocess` path. The Windows-Job and
> Linux-scope launches were called without internals, so `runnerInvocation` /
> `resolveRunnerInvocation` / `runnerAvailable` were silently ignored on **every
> managed production path**; only direct launch-function tests could reach them.

它还补了一个测试：「The isolated-runtime test now asserts the selected launch
receives all three seams and fails without the change.」

**③ 但这个修复至今没有合入 master。** 2026-11-26 直接读 master 源码
（`packages/subprocess/subprocess-local/src/index.ts`）确认：

```ts
// 第 215 行：internals 已经构造好了
const internals: SpawnInternals = { ...this.internals, onSpillFailure: this.reportSpillFailure }
if (containmentMode === 'fallback') {
  handle = spawnSubprocess(spec, internals)        // ← fallback 分支传了
} else {
  const binding = prepareManagedProcessBinding(internals)
  const linuxScope = containmentMode === 'linux-scope' ? this.linuxScopeDecision : undefined
  const launch = linuxScope === undefined
    ? launchWindowsJob(spec, env)                   // ← 仍未传 internals
    : launchLinuxScope(spec, env, linuxScope.literalArgv)   // ← 仍未传 internals
```

**为什么这件事极其重要：**

| 含义 | 影响 |
|---|---|
| 缺陷**已被第三方独立复现并修好** | 不需要再「说服维护者相信这是个 bug」—— 已经有人写了 patch |
| 修复带测试 | 降低了维护者的合并成本（他最担心的「改了会不会破」已有答案） |
| 但 **PR 通道关闭**（`has_issues=false`，仓库不接受 PR） | 修复只能靠维护者**手动 cherry-pick**，而他没有动作 |
| 已停滞 **19 天**（11-07 → 11-26） | 说明「有 patch」不足以推动合并，还需要**降低注意成本** |

**应当立刻做的事（优先级最高，成本最低）：**

1. **在 #12532 而不是只在 #11893 下留言** —— #12532 是重复议题里**先创建的那个**，
   而且有第三方修复挂在那里，维护者更可能看这一个。
2. 留言内容**不要重复论证**（已经论证清楚了），只做三件事：
   - 指出「修复分支存在但未合入」这个事实（附 commit 链接），
     让后续访问者一眼看到进展；
   - 提供**可直接 cherry-pick 的 patch 文件**（不用他去找分支）；
   - 附上**两个独立实现的验证**（本项目的 `test/vendor-seam-verify.js`
     + 该分支自带测试），说明「修好之后哪些东西会开始工作」。
3. **不要再新开第三个 discussion。** 已经有两个，再开只会分散注意力 ——
   这正是当前最大的问题（信息散落在两处）。

> **这一条改变了整个项目的处境。**
> 之前「唯一的硬阻塞」看起来像「没人理」；现在看清了：
> **有人理了、也修了，卡在「缺少一个让维护者顺手合并的入口」。**
> 而这个入口，恰恰是本项目最擅长提供的东西（完整的验证与取证）。

> 两者差 3 个数量级。

## 三、具体建议（按「投入产出比」排序）

### 🥇 第一优先：把方法论写成独立文章发出去（唯一可能破圈的动作）

**为什么这是第一优先**：见 §2.2。受众差 3 个数量级，且**不需要上游修复**、
**不要求读者用 Windows**、**不要求读者用 DSH**。

**已经准备好了**：
[`docs/articles/2026-11-26-我的基准测试说我的代码慢了20ms.md`](articles/2026-11-26-我的基准测试说我的代码慢了20ms.md)
—— 6 个真实案例、每条都有具体数字、结尾诚实交代项目现状。**待发。**

**发到哪（按目标受众匹配度排序）**：

| 平台 | 理由 | 注意 |
|---|---|---|
| **掘金** | 中文技术社区，性能/测试类文章有稳定流量 | 标题要具体数字，别用「浅谈」 |
| **V2EX / 分享创造** | 对「踩坑复盘」类内容接受度高 | 语气要平，别像广告 |
| **知乎**（问题下回答）| 「为什么基准测试不可信」这类问题下有长尾 | 回答而非文章，更容易被搜到 |
| Hacker News / r/programming | 英文受众最大 | **需要英文版**，见下 |

**标题候选**（都用「反直觉 + 具体数字」结构）：
1. `我的基准测试说我的代码慢了 20ms。错的是基准测试。`
2. `我踩了 6 次同一个坑：测量工具本身在骗你`
3. `宁可说"测不出来"：一次性能优化的 6 次自我欺骗`

**关键：文章里必须有一个「钩子」指向仓库。**
现在的草稿结尾确实提到了项目，但位置太靠后。
建议在**中段**（讲完第 2 个案例后）插一句：「这套判断我做成了一个小库，
无项目耦合，可以整文件拷走：[bench-verdict.mjs]」。

> ⚠️ **诚实提醒**：哪怕文章爆了，star 转化率通常也就 **1~3%**（阅读 → star）。
> 1000 阅读 ≈ 10~30 star。这不是失败，这是正常水平。
> 别指望一篇文章改变项目命运 —— 它能做的是**把人放进漏斗**。

### 🥈 第二优先：修掉「装完不生效」这个转化杀手

**现状**：新用户按 README 装完，插件**检测到上游缺陷 → 告警 → 停用自己**。

诚实地说，这个设计是对的（不假装在工作），但它意味着：
**每一个新用户的第一体验都是「它不工作」。**

**能做的三件事**：

1. **一行命令装好补丁**（已有 `node vendor/patch-dsh.mjs apply`），
   但要把它变成**安装流程的默认步骤**，而不是「安装前必读」里的第二段文字。
   建议：`npm i` 之后加一个 `postinstall` 提示（只提示不自动改，避免更可怕的信任问题），
   或者在 `plugin` 的首次启动日志里**直接打印那条命令**。

2. **把 discussion #11893 变成一个有进展的议题**。
   现在它 24 天没有更新。建议补一条评论，提供：
   - **可直接复制的复现脚本**（维护者最缺的是这个，不是论证）
   - 指出「上游在 3 个版本里保留了该参数、保留了局部变量，就是没传」
     —— 这是「不是忘了加，是那条路径没被测到」的强证据
   - 附上本项目的验证方法（证明补丁生效的那两个测试）
   
   > 维护者不修往往不是不认，是**优先级**。
   > 降低他们的行动成本（给 patch、给测试）比催促有效得多。

3. **在 README 顶部说清楚「什么时候不该用它」**。
   现在读者要读到很下面才知道「需要补丁」「Windows only」「受管环境装不上」。
   **提前劝退不合适的人，反而提高留下来的那批人的转化率** ——
   因为他们不会被「装完不生效」消耗掉。

### 🥉 第三优先：把「可发现性」的基础设施补齐

这些都是**低成本、一次性**的动作，但当前一项都没做：

| 项 | 现状 | 动作 | 预期作用 |
|---|---|---|---|
| **GitHub Discussions** | ❌ 关闭 | 开启 | 让提问不必开 issue；issue 列表不会被问题淹没；外部人更容易留下痕迹 |
| **仓库 About 的 homepage** | ❌ `null` | 填 npm 页面或文章链接 | 冷启动时多一个点击目标 |
| **Security 功能** | ❌ 全部 disabled | 开 secret scanning + Dependabot | 有徽章、显得在维护；也是 SECURITY.md 的配套 |
| **英文 README** | ❌ 只有中文 | 加 `README.en.md` | 打开英文受众（见 §2.1 障碍③）|
| **Topics** | ✅ 9 个 | 增加 `benchmarking`、`performance-measurement` | 让「方法论」相关内容也能被搜到 |
| **社交预览图** | ❌ 无 | 加 `og:image` / 仓库 social preview | 分享链接时有图，点击率差异明显 |

> 这些加起来大约 **1~2 小时**，但影响每一条外链的转化率。
> **在做任何推广之前先把这层做好** —— 否则等于把流量倒进一个漏的桶。

### 第四优先：把 star 的「理由」显性化

人们 star 一个仓库，通常因为以下之一。当前本项目的匹配情况：

| Star 的动机 | 本项目现状 | 建议 |
|---|---|---|
| 「我以后可能用得上」 | ⚠️ 需要补丁才能用 | 把「上游修好后零成本可用」写清楚 —— 这是**未来价值** |
| 「这个技术很酷」 | ✅ NativeAOT + 零依赖 + 1.2MB | 值得单独突出，现在埋在正文里 |
| 「这份文档/数据很有价值」 | ✅✅ 方法论 + 完整取证 | **最强项，但要让它独立可传播** |
| 「我想支持作者」 | ⚠️ 无个人故事 | 可以加一句「为什么做这个」，别长 |

**具体动作**：在 README 顶部「先读哪一篇」表上方，加一句三行的定位说明，类似：

> 一个 NativeAOT 写的 DSH 子进程 runner：**每次调用省 57~67% 的 runner 开销**。
> 附带一份**可复用的性能测量方法论**（6 个真实误判案例 + 一个无依赖的判定库）。
> 当前需要一个一行上游补丁 —— 上游修好后删掉 `vendor/` 即可。

这是「30 秒内让人决定要不要继续读」的位置，现在这块是空的。
