### S2 前置：IPC 阻塞点已解除

**最初发现的"重大障碍"及最终解法：**

| 阶段 | 发现 |
|---|---|
| 初查 | runner 用 `stdio[3]="ipc"`，是 Node 专有通道，AOT 无法接 |
| 一度结论 | 需要改 host 侧代码（fork DSH 内部实现） |
| **最终发现** | `ctx.subprocess` 是**官方公开的可替换 cordis 服务 seam** |
| 接入点 | `dsh-base/cordis.patch.yml:220` → `id: subprocess` |
| 机制 | 官方文档：patch 按 id 覆盖，**last write winning**，用户 patch 层最后应用 |

**结论：零源码修改，纯插件替换。** 且顺带实现了架构专家"问题 6"提出的"宿主内直接 spawn"思路。

## 二、阻塞问题：1.5-2s 启动延迟

### 现象

| 场景 | 耗时 |
|---|---|
| fdprobe（参考实现，AOT） | **48ms** |
| 最小 AOT（`Console.WriteLine("hi")`） | **45ms** |
| **dsh-aot-runner.exe（无参数立即退出）** | **1510-2348ms** |
| 内核侧（CreateProcessW→退出检测） | 38ms ✅ |

**runner 的内核操作只要 38ms，但进程整体要 2 秒。**

### 已排除的可能（都有实测对照）

| 假设 | 实验 | 结果 |
|---|---|---|
| 杀毒软件扫描 | 同一 exe 连续跑 6 次 | 全部 1.5-2.2s，排除 |
| stdio 句柄无效 | `ignore` / `pipe` / `inherit` 三种 | 都是 2s，排除 |
| overlapped 管道 | stdout 用 overlapped | 1885ms，排除 |
| JsonSerializerContext | 最小项目加源生成 | 47ms，排除 |
| P/Invoke + SafeHandle | 最小项目加 CreateJobObjectW | 46-62ms，排除 |
| 轮询线程 | 最小项目加 Thread.Sleep 循环 | 136ms，排除 |
| 静态 Stopwatch | 移除后重测 | 2328ms，排除 |
| 字符串插值 | 最小项目测 | 60ms，排除 |
| 模式匹配 switch | 最小项目测 | 43ms，排除 |
| DateTime/时区 | 最小项目测 | 55ms，排除 |
| csproj 配置 | 逐项对比 fdprobe | 几乎相同，排除 |
| 命名空间/程序集名 | 最小项目测 | 52ms，排除 |

### 已确认的关键事实

**极简 `JobRunner` + 原 `Program.cs` = 50ms**
**完整 `JobRunner` + 原 `Program.cs` = 1700-2300ms**

→ **问题确定在 `JobRunner.cs` 的代码内容里**，但逐个方法/特性单独测试都是快的。

这说明是**代码规模或特定组合**触发的 AOT 运行时行为，需要更系统的排查工具（如 `dotnet-trace`、AOT 的 `--verbose` 输出分析）。

## 三、这个问题的意义

### 如果无法解决

AOT 版的收益会被完全吃掉：

| | node runner | AOT（若有 1.7s 延迟） |
|---|---|---|
| runner 一跳 | 141ms | **1700ms** |
| 结论 | 基线 | **比 node 慢 12 倍** |

**方案会从"省 141ms"变成"慢 1.5 秒"，必须解决，否则整个 AOT 路线不成立。**

### 可能的方向

1. **系统排查 AOT 编译产物**：用 `ilc` 的 verbose 日志对比两个 exe 的生成差异
2. **怀疑点**：`JobRunner.cs` 里 39 个方法/字段的某种组合让 AOT 生成了大量可执行代码，
   触发加载阶段的页面调度
3. **验证方法**：把 `JobRunner.cs` 按方法二分之一分割，二分定位（本次尝试因正则工具
   不可靠而未完成，需要人工做）
4. **替代方案**：如果定位困难，可考虑把 `JobRunner` 拆成多个小类/文件再试
