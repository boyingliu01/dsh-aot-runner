# 测试覆盖率：现状、口径、以及「哪些缺口是补不上的」

> **最后核实**：2026-11-26
> **数据来源**：本机 `dotnet test --collect:"XPlat Code Coverage"`，取最新一份 cobertura。
> **复跑**：`./build.sh --check`（其中一步就是 C# 单测 + 覆盖率）

这份文档存在的理由：**「覆盖率多少」这件事在本项目里被反复误读过**，
而且外部审视拿到过一份过时的数字（「`JobRunner` 19.8% / `IpcChannel` 0%」），
据此建议「补测到 40%」。实际情况与此相差很远，与其下次再被误读，不如把口径固定下来。

---

## 一、现状（2026-11-26 实测）

| 指标 | 数值 |
|---|---|
| **生产源码行覆盖** | **100.00%**（`build.sh --check` 口径：878/878；按 class×行 去重后 2192/2192。两种数法都 100%，见下方注） |
| **生产源码分支覆盖** | **744 / 776 = 95.88%** |
| 未覆盖行 | **0** |
| 未达 100% 的分支行 | **28 处**（全部在下面 §三 逐条列出） |
| C# 测试用例数 | **346**（2026-11-26 由 340 增至 346） |
| JS 侧（`plugin/lib`）行覆盖 | 89.48%（`coverage-summary.json`，Gate 5 地板 80%） |
| 契约分支区间覆盖 | **30.71%**（Node 22 基线 43/140；本机 Node 26 实测 27.7% = 44/159。见 §二/§三，**这是另一个东西**） |

> 「生产源码」= `src/` 下的 C# 文件。测试辅助类（`tests/` 里的 `FakeChannelIo` 等）
> 不计入 —— 它们的覆盖率取决于被测用例怎么用，不是质量信号。
>
> **为什么两个行数（878 vs 2192）？** `scripts/coverage-summary.py` 按
> 「类 × 不同行号」去重计数（同一个文件里多个类共享的行只算一次），
> 得到 878；而按 cobertura 的 `<class>` 逐条枚举（泛型/内嵌类型会重复出现）
> 得到 2192。**两者都取到 100%**，结论一致；引用时请注明是哪一种数法，
> 否则两个人都对却看起来互相矛盾 —— 这正是本文档要避免的那类混乱。

## 二、三个容易混淆的「覆盖率」，请分开看

本项目同时存在**三种**完全不同的覆盖率数字。它们的分母、工具、用途都不同，
混为一谈会导致错误的行动结论（2026-11-26 的外部审视就混了一次）。

| # | 名称 | 分母是什么 | 当前值 | 谁在读它 | 它回答什么问题 |
|---|---|---|---|---|---|
| 1 | **C# 生产源码覆盖率** | `src/*.cs` 的行/分支 | 100% 行 / 95.88% 分支 | `build.sh --check`、Gate 5（地板 99%） | 「我写的 C# 有没有被测试跑到」 |
| 2 | **JS 插件覆盖率** | `plugin/lib/*.js` | 89.48% | Gate 5（地板 80%） | 「插件胶水层有没有被跑到」 |
| 3 | **契约分支覆盖率** | **上游 DSH 的 `runner-launch-*.js`** | 30.71%（Node 22 基线 43/140）<br>本机 Node 26 实跑 27.7%（44/159） | `scripts/contract-branch-coverage.mjs --check` | 「DSH 契约里有多少分支被我们的用例走到」 |

**第 3 项的分母不是我们的代码** —— 它是上游那个 57KB 的打包产物。
它的分子取决于 `COVERAGE_CASES` 里列了几条驱动用例（当前 5 条）。
所以「契约覆盖率 30%」不代表「本项目的测试覆盖率 30%」。

## 三、契约覆盖率（第 3 项）的 30% 是怎么来的，以及为什么它有天花板

### 为什么低

> **两个数字不要混用**：`.contract-coverage.json` 基线是在 **Node 22** 上采的（43/140 = 30.71%），
> 而本机是 **Node 26**，同一个契约文件采出来是 44/159 = 27.7%。
> 分母不同是因为 V8 的**分支区间划分方式**随主版本变 —— 这也正是基线要绑 `nodeMajor`、
> 跨版本直接报 exit 4 的原因（见 [ADR-0001](adr/0001-contract-coverage-ratchet.md)）。
> 下面说「30%」时指的是基线口径，说「27.7%」时指的是本机 Node 26 口径，两者都真实，但不可比。

契约文件 `runner-launch-B2zsQ1Dz.js` **同时包含 Windows、Linux、macOS 三条路径的实现**
（实测 linux 相关 53 处、win32 18 处、Posix 类 15 处）。
在 Windows 上跑再多用例，也走不到 POSIX 那部分函数里的任何一个（本机分类为「跑不到」的是 15 个，实际涉及的 Linux 代码块更多）。

`scripts/contract-branch-coverage.mjs` 的 `classifyUncovered()` 已经把这件事分成了两类：

- **本平台跑不到的（POSIX/Linux 专属）**：结构性不可达，不是缺口
- **可能该补测的**：真正可以努力的部分

本机实测（Node 26）：未覆盖函数 **90 个**，其中「本平台跑不到」**15 个**、
「可能该补测」**75 个**。注意这 75 个里包含大量 Linux/macOS 分支的辅助函数 ——
分类器只按**函数名**里的 `linux|posix` 判，识别不到「名字看不出是 POSIX 的」
（例如 `epollHasStdin`、`linuxDeviceNumber` 的调用方）。所以 75 这个数字是**上界**，
不是「75 个用例就能补完」。

### 天花板在哪

`COVERAGE_CASES` 当前 5 条（基本命令 / 不存在文件 / 非零退出 / 带引号参数 / PATH 解析）。
把它们扩到 20 条能提高百分比，但**边际价值递减且采集成本线性增长**
（单次采集约 17 秒，`--check` 疑似回退时还要重采 3 次）。

更关键的是：**契约覆盖率的价值是「看趋势与缺口」，不是「冲数字」。**
它现在作为门禁的作用是**防回退**（基线 `.contract-coverage.json` + 四态退出码，
见 [ADR-0001](adr/0001-contract-coverage-ratchet.md)），
这个作用已经成立 —— 删掉一条用例会被拦住。

### 如果将来要提高，正确的做法

1. **增加平台维度的分母**：在 Linux CI 上跑一次同名采集，把 POSIX 部分补上
   —— 这是唯一能把「结构性不可达」变成「可达」的办法；
2. **而不是**在 Windows 上堆用例堆到 40%，那样得到的是一个「看起来更好看的数字」，
   对真实缺陷的发现能力几乎没有提升。

这条判断已经在 ADR-0001 的「被否决的备选方案」里记过同类推理：
**不要为了数字好看而改变判据口径。**

## 四、生产源码剩下的 28 处未达分支：逐条说明

这些**都是真实缺口，但一部分在当前测试架构下补不上**。
写出来是为了让下一个人不必重新查一遍，也为了说明「95.88% 不是没努力」。

| 类 | 行 | 情况 | 能补吗 |
|---|---|---|---|
| `ExecutableResolver` | 121 | `BuildSearchRoots` 的 4 个分支中 1 个未走（依赖特定 PATH 形态） | ⚠️ 需要构造特定 PATH 环境 |
| `Win32ChannelIo` | 72 | `WriteFile` 失败分支 | ⚠️ 需要真实的写失败（管道已关闭但句柄未释放） |
| `JobRunner` | 71 | `ProgramName` 在 `argv` 为空时返回 null | ⚠️ 需要构造空 argv 的 runner 实例 |
| `JobRunner` | 388 | `Dispose` 的一条 `if` 分支 | ⚠️ 需要特定释放顺序 |
| `JobRunner` | 116 | `Poll` 中 `IsJobEmptiable() && _resultDelivered` 的组合 | ❌ 竞态：两个条件同时成立的窗口极窄 |
| `JobRunner` | 203 | `TryReadExitCode` 的一条分支 | ⚠️ 需要 `GetExitCodeProcess` 失败 |
| `JobRunner` | 66 / 96 | `EmitCreateProcessError` / `PublishResult` 的各一条 | ⚠️ 需要特定的 Win32 失败注入 |
| `ProcessLauncher` | 150 | `ResumeSuspendedThread` 的失败分支 | ❌ 需要 `ResumeThread` 返回失败（几乎不可能自然触发） |
| `ProtocolJson` | 67 | `GetString() ?? fallback` 的 `??` 侧 | ✅ 已确认**不该被走到**（空串取出来是 `""` 不是 null），2026-11-26 已加测试钉住这个结论 |
| `ProtocolJson` | 78 | `ReadEnvInto` 的 4 个分支中 1 个 | ⚠️ JSON 解析器层面的边界 |
| `TargetSpawner` | 85 / 414 | `Spawn` 与 `ResumeThreadCore` 的失败分支 | ❌ 同 `ResumeSuspendedThread` |
| `Trace` | 82 | `Write` 的一条分支 | ⚠️ 需要 Trace 停在停在边界状态 |

**结论**：剩下的缺口主要是**Win32 API 失败路径**与**极窄竞态窗口**。
为它们强造测试的代价（注入真实的 API 失败）高于收益，且容易写出
「只在测试里成立的假路径」—— 那种测试给出的是虚假信心，比 4% 的分支缺口更糟。

> **这与「373 行 vs 7 行」那类问题同源**：数字本身不是目的，
> 数字背后的「我们到底验证了什么」才是。§五给了替代做法。

## 五、比补覆盖率更有效的两件事

如果目标是「减少上线后的意外」，按性价比排序：

### 1. 变异测试（已在用）

覆盖率告诉你「代码被执行过」，变异测试告诉你「测试能不能发现错」。
本项目已有 `StrykerOutput/` 与 `bench/coverlet-crash-ab.js` 的实践，
并在 `docs/TODO.md` §4.1 记录了准则：

> 新增任何自检后，**故意改坏被测对象，确认它会红**。

2026-11-26 本轮就用了这个方法验证新加的测试：
把 `ProtocolJson.GetStringOr` 的类型检查改成 `if (false)`，
新增的 `ParseStart_字段类型不对时回退而不是抛异常` 立刻变红 ——
**这才说明这条测试在做事，而不只是把某个数字推高。**

### 2. 接缝测试（比覆盖率更能防真实事故）

`test/vendor-seam-verify.js` 是个例子：它证明的不是「某函数被调用过」，
而是「**补丁生效时，host 真的改用了 AOT exe**」——
这个判据直接对应「用户装完能不能用」，比任何百分比都更接近真实风险。

## 六、如何自己复跑

```bash
# 全量（含 C# 单测 + 覆盖率 + 其余门禁，约 2 分钟）
./build.sh --check

# 只要 C# 覆盖率
dotnet test tests/DshAotRunner.Tests/DshAotRunner.Tests.csproj \
  --collect:"XPlat Code Coverage" \
  --settings tests/DshAotRunner.Tests/coverage.runsettings

# 契约覆盖率（第 3 项）
node scripts/contract-branch-coverage.mjs            # 报告
node scripts/contract-branch-coverage.mjs --check    # 门禁（四态退出码）
```

> 契约覆盖率必须用**与基线相同的 Node 主版本**跑（基线绑定 `nodeMajor`）。
> 本机 Node 26 会对基线 v22 报 exit 4（「基线过期」），这是**设计意图**不是缺陷 ——
> 详情见 [ADR-0001](adr/0001-contract-coverage-ratchet.md) 与 `build.sh` 里那段注释。
