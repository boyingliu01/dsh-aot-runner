# 依赖清单

> 目标：证明 NativeAOT 产物**零外部运行时依赖**，可以直接分发给没有装
> .NET SDK / VC++ 可再发行包的机器。
>
> 检查脚本：`./scripts/check-deps.sh`（构建后自动可跑）

---

## 一、结论

**产物只依赖 Windows 自带组件**，无 VC++ 运行时、无 .NET 运行时。

| 检查项 | 结果 |
|---|---|
| `vcruntime140*.dll` | ✅ 无 |
| `msvcp140*.dll` | ✅ 无 |
| .NET 运行时（coreclr / hostpolicy / clrjit） | ✅ 无 |
| 用 `dumpbin /DEPENDENTS` 验证 | ✅ 见下表 |
| 在剥净环境变量下运行 | ✅ 通过 |

## 二、完整依赖清单

`dumpbin /DEPENDENTS dist/dsh-aot-runner.exe` 的输出：

| DLL | 来源 | 说明 |
|---|---|---|
| `KERNEL32.dll` | Windows | 核心 API |
| `ADVAPI32.dll` | Windows | 安全/注册表 |
| `bcrypt.dll` | Windows | 加密原语（Vista+） |
| `ole32.dll` | Windows | COM 基础设施 |
| `api-ms-win-crt-heap-l1-1-0.dll` | Windows 10+ | UCRT：堆 |
| `api-ms-win-crt-math-l1-1-0.dll` | Windows 10+ | UCRT：数学 |
| `api-ms-win-crt-string-l1-1-0.dll` | Windows 10+ | UCRT：字符串 |
| `api-ms-win-crt-convert-l1-1-0.dll` | Windows 10+ | UCRT：类型转换 |
| `api-ms-win-crt-runtime-l1-1-0.dll` | Windows 10+ | UCRT：运行时 |
| `api-ms-win-crt-stdio-l1-1-0.dll` | Windows 10+ | UCRT：stdio（`_get_osfhandle` 所在） |
| `api-ms-win-crt-locale-l1-1-0.dll` | Windows 10+ | UCRT：区域设置 |

**这些都是 Windows 10 及以上自带的系统组件。** `api-ms-win-crt-*` 是 UCRT 的
API set 转发 DLL，不是需要单独安装的可再发行包 —— 这一点容易误解：
它看起来像第三方依赖，实际是 OS 的一部分。

> 注意：清单里没有 `ucrtbase.dll` 本体，只有 `api-ms-win-crt-*` 转发层。
> 两者等价 —— 转发层最终解析到 `ucrtbase.dll`，由 Windows 提供。

## 三、验证方法与可复现步骤

### 1. 依赖检查（自动）

```bash
./build.sh                 # 先构建
./scripts/check-deps.sh    # 检查依赖
```

脚本会：
- 拦截 `vcruntime*` / `msvcp*` / `msvcr*` / `concrt*` / `vccorlib*`
- 拦截 `coreclr` / `hostpolicy` / `clrjit`
- 对白名单外的依赖给出 WARN（不直接失败，因为不同 Windows 版本可能有差异）

### 2. 脚本自身可信吗

做过反向自校验：拿一个**确实依赖 VC++ 运行时**的 exe
（`MSVC/…/bin/Hostx64/x64/cl.exe`）喂给脚本：

```
[ FAIL ] 出现 VC++ 运行时依赖: VCRUNTIME140.dll
[ FAIL ] 出现 VC++ 运行时依赖: MSVCP140.dll
==> 依赖检查未通过
```

脚本能正确识别并拦截，不是只会亮绿灯。

### 3. 剥净环境运行（已实测）

只给 Windows 启动所必需的最小环境，**不含任何 `DOTNET_*` 变量、不含 .NET 安装目录**：

```js
const env = {
  SystemRoot: 'C:\\Windows',
  PATH: 'C:\\Windows\\system32',
};
```

结果：

```
target 输出: "CLEAN_ENV_OK"
协议结果  : {"type":"target-exit","exitCode":0}
```

**exe 在无 .NET 痕迹的环境下正常完成了 spawn、执行、回报退出码的全流程。**

## 五、如果将来出现 VC++ 依赖怎么办

按可能性排序的常见原因：

1. **误用了非 NativeAOT 的构建方式** —— 确认 `dotnet publish` 带了 `-r win-x64`
   且 csproj 里有 `<PublishAot>true</PublishAot>`
2. **某个 NuGet 包带了原生 VC++ 编译的组件** —— `dumpbin` 会显示出具体是哪个，
   据此判断能否替换
3. **链接了静态库的 DLL 导入** —— 检查 `IlcLinkArgs` 里是否误加了 MSVC 的导入库

排查起点：

```bash
./scripts/check-deps.sh    # 先看清单里多了什么
grep -n "PublishAot\|IlcLinkArgs\|NativeLibrary" DshAotRunner.csproj
```
