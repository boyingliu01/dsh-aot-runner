# 隔离价值量化：独立 runner 进程到底值多少

> 对应 issue #16。实验脚本：[`bench/isolation-value.js`](../bench/isolation-value.js)
>
> 复现：`node bench/isolation-value.js`（全部场景，约 90 秒）
> 或 `node bench/isolation-value.js --scenario fork`（单个场景）

---

## 先说结论

**「独立 runner 进程」的隔离价值，在这四个场景里只在一个场景成立，而且是唯一真正重要的那个：**

| 场景 | 内联（无 runner） | 走 runner | 隔离有价值吗 |
|---|---|---|---|
| 1. target 崩溃 | host 正常完成 | host 正常完成 | ❌ 无差异 |
| 2. target 海量输出 | 卡住 | 卡住 | ❌ 无差异（且两者都卡） |
| 3. target 挂起 | host 保持响应 | host 保持响应 | ❌ 无差异 |
| 4. **target 崩溃 + 遗留 detached 子孙** | **5 个孤儿全存活** | **5 个全部回收** | ✅ **唯一有差异的场景** |

所以：**这一层进程边界的价值不是"防崩溃"（Windows 的进程隔离本来就防住了），
而是"防进程泄漏"—— Job Object 会回收 target 死后遗留的孤儿进程。**

这个结论与项目原来的论证方向不同。原来写的是「target 崩溃不拖垮 host」，
但实测发现那件事**不需要 runner 也能做到**。

---

## 实验设计

### 对照组怎么构造

「内联」与「走 runner」真正的差别是**中间隔了几层进程边界**：

```
内联:    host ────────────► target            (1 层)
runner:  host ──► runner ──► target           (2 层)
```

对照组不能拿 node runner 当基线 —— 那样测的是「两种 runner 谁更抗故障」，
不是「这一层隔离本身值多少」。所以内联组是 host **直接** spawn target。

runner 组必须走**真实调用契约**，所以复用 `test/runner-client.js` 的
`launchRunner`（`stdio[3]='ipc'` + start 请求 + target 的 stdio 在 fd 5/6）。

> 这里踩了个坑，记录在脚本注释里：自己拼 `spawn(AOT, ..., {stdio:[...,'ipc',...]})`
> 然后调 `c.stdio[3].send()` 会拿到 `null` —— Node 只给 node 子进程提供 `.send`。
> 更糟的是**它不报错**：runner 静默等待，8 秒后被判成「host 被害」，
> 实验会得出一个完全错误却很有说服力的结论。

### 判据

所有判据都是**二值事实**（存活 / 回收 / 有没有输出），不是毫秒数。
所以本实验**不受机器负载影响**，不需要等 CPU 降下来 —— 这与
`bench/aot-observe.js` 那类时延测量有本质区别。

---

## 场景 1：target 崩溃

**做法**：target 执行 `process.abort()`（真正的 native abort，不是 JS throw ——
throw 能被 try/catch 兜住，测不出隔离）。

**结果**：

| 组 | host 仍在运行 | 有结果输出 | 正常完成 |
|---|---|---|---|
| 内联 | false | true | **true** |
| runner | false | true | **true** |

两组都是「跑完自己退出」，**host 都没有被害死**。

**结论：此场景无隔离差异。**

> 第一版这里判错了：我把「8 秒后 `isAlive()===false`」一律当成「host 死了」，
> 于是内联组（跑完就自己退）被判成「被害」，结论看起来支持隔离假设。
> 实际要区分「正常完成后退出」和「中途被害」—— 前者有结果输出，后者没有。

---

## 场景 2：target 海量输出（约 200MB）

**做法**：target 往 stdout 狂写，host **故意不读**（模拟 host 忙、来不及消费）。

**结果**：两组都卡住。

**结论：多一层 runner 并不解决背压问题。**

这条值得单独说，因为它推翻了「多一层转发更安全」的直觉：
runner 也要把 target 的输出转发出去，转发不出去时它同样会阻塞。
隔离**不改变**管道语义 —— 谁在最下游不读，整条链都会卡。

> 真实 DSH 里 stdout 走独立 fd 且有背压处理，所以生产路径不会这么容易卡。
> 本场景证的是「这一层隔离本身不提供背压保护」，不是说 DSH 有 bug。

---

## 场景 3：target 挂起不退出

**做法**：target `setInterval(()=>{},1000)` 永不退出，host 同时跑一个 10ms 的定时器，
看还能不能调度。

**结果**：内联 95 次 tick，runner 95-96 次 tick，**两组一致**。

（理论预期 ~150 次；本机 CPU 长期 100%，实际调度被压缩，但**两组一致**说明对比有效。）

**结论：此场景无隔离差异。** host 用异步 spawn，本来就不会被 target 挂住。

---

## 场景 4：target 崩溃 + 遗留 detached 子孙（**唯一有差异**）

**做法**：target 派生 5 个 `detached: true` 且 `unref()` 的子进程（脱离父子关系，
父死不会自动带走），600ms 后自己 `process.abort()` 崩溃。
然后逐个检查那 5 个具体 PID 是否存活。

**结果**：

| 组 | 派生子进程 | 崩溃后仍存活 | 残留 |
|---|---|---|---|
| 内联 | 5 | **5** | **5 个孤儿** |
| runner | 5 | **0** | **0** |

**结论：Job Object（`KILL_ON_JOB_CLOSE`）确实回收了 target 死后遗留的孤儿进程。
这是本实验里隔离唯一的实测价值。**

### 这个场景改了四次，每次结论都不同

过程比结论更值钱，全部记在脚本注释里：

| 版本 | 做法 | 结果 | 问题 |
|---|---|---|---|
| 1 | target 正常退出，数全机 node 进程总数 | 两组都"残留 0" | **没测到**：基线飘、窗口短，`峰=7` 说明子进程根本没被数进去 |
| 2 | target 打印 5 个 PID，正常退出后逐个查 | 两组都 0 残留 | **结论是真的，但测不出 Job Object**：正常退出时 Windows 自己会清理 |
| 3 | 子进程 `detached`，外部 `taskkill /F` 杀 runner | 两组都 5 残留 | **杀法不对**：`taskkill /F` 不保证走 job handle 关闭语义 |
| 4 | 子进程 `detached`，**target 自己崩溃** | 内联 5 / runner 0 | ✅ 这才是对的场景 |

第 3 版的教训尤其值得记：我当时以为发现了「runner 的 Job Object 不生效」这个
缺陷，正准备写进 issue。查下去才发现是**我杀 runner 的方式**不对 ——
真实场景里 runner 是正常退出或从未被误杀，不会走 `taskkill /F`。

**如果没查这一步，就会报一个不存在的缺陷。**

---

## 可复用的做法

1. **「对照组」要对着真正想量的那个变量构造。**
   想量「这一层进程边界值多少」，对照组就不能是「另一种 runner」。
2. **二值判据免受负载干扰。** 只要判的是「存活/回收」而不是「多少毫秒」，
   就不需要等机器空闲 —— 这让实验中集群上也能跑。
3. **数总量不如追踪具体 PID。** 第一版数全机进程数，遇到基线漂移就失效；
   拿到 target 打印的 5 个 PID 后，每个进程要么活着要么没了，没有模糊地带。
4. **实验得出"看起来像 bug"的结论时，先怀疑实验本身。**
   本实验第 3 版差点让我报一个不存在的 runner 缺陷。
5. **负面结果要说出来。** 4 个场景里 3 个没有差异，这比只报 1 个正结果更诚实，
   也更能指导定位（隔离的价值在进程泄漏，不在崩溃防护）。

---

## 对 README 的影响

原论证：「runner 作为独立进程存在的理由不是快，是隔离（target 崩溃不拖垮 host）。」

实测后应改为：

> runner 作为独立进程的理由有两个：
> 1. **更快**（AOT 二进制，实测 p50 从 ~276ms 降到 ~114ms）
> 2. **防进程泄漏**（Job Object 回收 target 死后遗留的孤儿进程；
>    实测内联方案残留 5 个孤儿，runner 方案 0 个）
>
> 「防崩溃」不是理由 —— 实测 target 崩溃时内联方案 host 同样存活，
> Windows 的进程隔离本来就够用。
