## 一、项目目标评估

### 1.1 目标本身：清晰且真实

README 的定位是准确的 —— **用 NativeAOT 可执行文件替换 DSH 的 Node.js 子进程 runner**，
换掉链路中间那个每次都重新加载 Node 运行时的转发进程。

这个目标：
- **有真实痛点**（每个子进程调用白付 ~200ms）
- **收益可量化**（本次实测收益比例 63.5%~66.6%）
- **边界明确**（实现的是与 node 版**相同的 Node IPC 协议**，不是自创协议 —— 这点很关键，意味着 host 侧零改动）

### 1.2 但「正式发布」这个时机需要重新定义

README 顶部有一句极重要的警告，被这次「公开发布」的诉求冲淡了：

> **当前需要上游补丁才能生效** —— 在 DSH 0.2.0-rc.2 上，本插件必须配合一个 1 行的上游补丁才能工作。

这意味着：**任何陌生人 `npm install` 之后，插件会自己检测到缺陷、告警、然后停用自己。**

从工程诚实性角度看这是**优秀设计**（"明确告警并停用自己，而不是假装在工作"）。
但从「正式发布」角度看，它决定了一件事：

> **这不是一个"装上就能用"的产品，而是一个"需要用户先给自己打补丁"的工具。**

这不是缺陷，但它必须成为发布材料的**第一句话**，而不是第 6 行的一个 blockquote。

**建议的定位措辞：**

> dsh-aot-runner 是一个 NativeAOT runner 实现，配合**一个 1 行上游补丁**可让 DSH 子进程调用快 60%+。
> 上游修复后（discussion #11893），本补丁即可删除。
> 由于需要修改 node_modules，本工具定位为**进阶用户/技术尝鲜**，而非开箱即用。

### 2.2 值得肯定的测试设计

这个项目的测试**明显高于一般水平**，有几个设计点值得保留：

1. **探针自校验**（`leak-verify.js`）：先证明"监视器真的能看到进程"，再验证零泄漏。
   甚至有一条**反向测试**：「泄漏检查会失败」—— 故意留活进程，断言检测器必须报错。
   > 这是防止「测试永远为真」的正确做法，见第五节的对比。

2. **A/B 不是只比"两边一致"**：还有 `expectStdout` / `expectErrorShape` 做独立的
   **结构化断言**。理由是"两边同时错也会通过" —— 这是很多人会漏掉的一层。

3. **错误对象字段集严格比对**：`assert.deepStrictEqual(actualKeys, expectedKeys)`，
   区分了「字段缺失」与「字段为 null」。而这正是 `isSerializedRunnerError` 会丢弃整条错误的真实原因。

4. **host 路径测试装了观测点**：不只断言 exitCode===0，而是断言 launcher **实际启动的就是 AOT exe**。
   （CHANGELOG 记录了这次修复：此前 node runner 也能让测试通过，插件失效时测试照样全绿。）

### 2.3 重构后的行为一致性：验证通过

用户最担心的是「大面积重构后没测过」。从结果看：

- **重构没有引入行为回归**：28 项 A/B 逐字节一致，包括最容易因重构出错的三处：
  - 帧解码器拆分（`IpcFrameDecoder`）→ 多帧/半帧/大消息全部正确
  - argv 解析拆分（`ArgParsing`）→ 首项 `--` / `.js` 前缀 两条路径都正确
  - 句柄清理收敛为 `ReleaseHandle<T>` → 100 次零泄漏 + 竞态 5/5

- **重构消除了真实缺陷**：`git log` 里记录了三个由重构暴露并修复的严重缺陷：
  - `2bc9c48` 消除复杂度与重复代码违规（CCN > 5 → 0）
  - `9ae2ecc` **`SafeJobHandle.IsEmpty()` 恒返回 false**（两处叠加的 Win32 调用错误）
  - `0b3a540` 拆分 IpcChannel 帧解码与 ArgParsing，为引入单测做准备

  `IsEmpty()` 恒 false 这个缺陷尤其值得注意：它是**静默失效**——
  「job 空了就收尾」这条路径从来没生效过，而所有 e2e 测试仍然是绿的。
  最终是靠**补上单元测试**才抓到的。这恰好印证了重构的正确方向。

## 三、性能评估

### 3.1 本次实测数据

**单次基准**（`bench/d1-ab-bench.js`，n=30，CPU 31%→48%）：

| 实现 | p50 | p95 | p99 |
|---|---|---|---|
| 原生地板（hostname） | 44ms | 222ms | 707ms |
| node runner | 308ms | 660ms | 781ms |
| **AOT runner** | **141ms** | **374ms** | 793ms |

- 净收益：**168ms/次，收益比例 63.5%**
- 失败样本：node=0, AOT=0
- 输出抽样：两者 `stdout` 完全一致（`"伯英的X1C\n"`）

**多轮观测**（`npm run observe`，3 轮 × 40 次）：

```
第 1 轮: node 336ms → aot 139ms  净省 197ms (66.6%)
第 2 轮: node 303ms → aot 125ms  净省 178ms (67.5%)
第 3 轮: node 407ms → aot 171ms  净省 236ms (66.1%)
判定: 单轮离散度均超限 → 只采信比例（3 轮跨度 1.4pp）
```

### 3.2 判定：项目对性能的表述是**诚实**的

值得特别肯定的一点：**基准脚本自己给出了 `verdict: UNRELIABLE`**，
并明确说明「离散度 100.1% > 10%，系统干扰过大」。

它**没有**把一个漂亮但虚假的数字当成结论。这正是 `docs/测量方法论` 里那 5 条踩坑的产物，
也在本次评估中被独立验证有效 —— 因为我在 CPU 48% 的负载下跑，它如实报告了不可信。

同时，**收益比例被证明是稳定指标**：本次 63.5% / 66.6% / 67.5% / 66.1%，
与仓库历史记录（64.1% / 66.6%）和文档宣称（59%~66%）**落在同一区间**。
README 里那句「收益比例是稳定指标，绝对值不是」是**有实证支撑的**。

### 3.3 但性能文档有内部矛盾（需修正）

同一条收益在仓库里有**三个不同说法**：

| 位置 | 说法 |
|---|---|
| `README.md` 开头 | 省 **92~94ms（约 59%）** |
| `plugin/README.md` 开头 | 省约 **130~141ms**，消除 **65.0%** |
| CHANGELOG 0.1.0 | 省 **92~94ms（约 59%）** |
| 本次实测 | **168ms / 63.5%**、**197ms / 66.6%** |

`plugin/README.md` 里甚至同时写了 `65.0%` 和 `59.1%~59.6%` 两个比例。
**发布前必须统一口径**，否则第一个技术 reviewer 就会指出这个自相矛盾。

## 五、🔥 最重要的问题：护栏的可信度

**如果你只看一条，请只看这条。**

先说结论：**测试本身是可信的，行为层面的验证没有发现问题。**
但**「覆盖率门禁」这一道自动化护栏实际上没有在工作** —— 它输出的数字是假的（0.0%）。
这意味着：**测试通过是可信的，但"覆盖率达标"这个信号不可信**。

> ### ⚠️ 已撤回的错误结论（自我更正记录）
>
> 本报告初稿曾断言「`test/e2e-plugin-verify.js` 与 `test/host-path-verify.js` 里存在
> `proto` 空断言，永远为真」。**经 grep 复核，这条结论是错误的，已全部删除。**
>
> 事实是：这两个文件里**根本没有 `proto` 变量**。`proto` 只存在于 `test/runner-client.js`
> 的 `runAot()` 中，且第 352 行有真实累加：
> ```js
> c.on('message', (m) => {
>   if (!m) return;
>   if (m.type === 'target-exit' || m.type === 'error') { fin(null, m); return; }
>   proto += JSON.stringify(m) + '\n';   // ← 收集"多余协议噪音"，非终态消息才会到这里
> });
> ```
> 它是**为「不该出现的非终态消息」设计的收集器**，逻辑正确。
> `runNode()` 里没有 `proto` 是合理的，因为该函数用 `fin(null, m)` 提前返回、不走这条分支。
>
> 我当初的"恒为真"现象，来自我自己临时写的探针脚本没有订阅 `message` ——
> **那是我的测量脚本的缺陷，不是项目代码的缺陷。**
> 这恰好又一次印证了项目 `docs/测量方法论` 的元规则：
> **当测量结果反复"不合理"时，先怀疑测量工具。**

### 5.1 缺陷：覆盖率门槛实际上没在跑

`scripts/coverage-summary.py` 用 `glob.glob(...)` 后直接取 `files[0]`：

```python
files = glob.glob("tests/**/coverage.cobertura.xml", recursive=True)
per_class = collect(files[0])          # ← 取第一个，不是最新的
```

`glob` 返回**文件系统顺序**（实测非时间序），而 `TestResults/` 下已经累积了 **14 份**历史报告。
其中 **4 份是 `lines-valid="0"` 的空报告**。

**实测结果**：`files[0]` 恰好选中了一份空的，于是输出：

```
生产源码:    0.0%  (0/0 行)
测试代码:    0.0%  (0/0 行)
合计:        0.0%  (0/0 行)
```

**真实覆盖率**（我从最新的有效报告独立算出来）：

| 类 | 覆盖率 | 说明 |
|---|---|---|
| `ProtocolJson` | **100.0%** | 100/100 |
| `CrtDescriptorTable` | **100.0%** | 36/36 |
| `LineReader` | **100.0%** | 32/32 |
| `ArgParsing` | **100.0%** | 15/15 |
| `Trace` | **100.0%** | 14/14 |
| `IpcFrameDecoder` | **95.8%** | 46/48 |
| `SafeJobHandle` | 77.1% | 27/35 |
| `SafeKernelHandle` | 66.7% | 2/3 |
| **`JobRunner`** | **19.8%** | **112/567 ← 核心类，最大的风险面** |
| **`IpcChannel`** | **0.0%** | **0/64** |
| **`NdjsonChannel`** | **0.0%** | 0/18（调试通道，可接受） |
| **`Native`** | **0.0%** | 0/4（P/Invoke 声明，可接受） |
| **生产源码合计** | **41.3%** | **388/940** |

**重要**：41.3% 这个数字**不代表质量差** —— `JobRunner` 和 `IpcChannel` 的行为
是被 77 项 e2e 覆盖的（A/B 28 项、IPC 6 项、泄漏 7 项、竞态 5 项都在打这两个类）。
但它们**没有单元测试级别的保护**，一旦重构出错，报错点会很模糊。

`IpcChannel` 是 0% 单元覆盖里最需要关注的：它是**与 host 通信的唯一通道**，
而它内部有大量"实测出来的行为"（`ERROR_BROKEN_PIPE` 判定、`WriteFile` 部分写循环）。
好消息是 `IpcFrameDecoder` 被拆出去了（95.8%），这部分最容易出错的字节逻辑有了保护。

### 5.2 这解释了用户担心的那件事

用户说「担心重构后有问题」。诚实的回答是：

- **本次行为层面「没发现问题」是可信的**（216 项测试真的跑了，A/B 逐字节一致）
- **覆盖率门禁输出的数字不可信**（真实值 41.3%，脚本却报 0.0%）
- 但**「测试能否拦住未来的回归」这个信心是站得住的** ——

这两件事必须分开说。前者说明**当前代码是好的**，后者说明**护栏有洞**。

我执行了 `./build.sh --clean`，结果是：

### 6.2 根因

**NativeAOT 在 Windows 上强制要求 MSVC 链接器**，无法用 `ld.lld` 或 MinGW 替代。

### 6.3 我的失误（需明确记录）

`--clean` 会执行 `rm -rf obj bin "${OUT_ABS}"/*`，把 `dist/dsh-aot-runner.exe` 一起删掉了。
**这是我造成的，且该文件不可恢复**：

- ❌ 不在 git 历史里（`.gitignore` 排除 `*.exe`，`git rev-list --objects --all` 确认无 .exe 对象）
- ❌ 回收站里没有
- ❌ `%TEMP%` 里没有

**缓解措施**：`plugin/bin/dsh-aot-runner.exe`（同一份产物，md5 `ed1cdddd…`）**幸存**，
我已把它复制回 `dist/`，因此本次评估的**全部动态测试都是用真实产物跑的**，结论有效。
两份文件 md5 一致，且 `plugin/bin/` 被 `.gitignore` 排除 —— 这是 `build.sh` 末尾的同步步骤救了我。

> 我现在已在 `/tmp/aot-surviving.exe` 额外保留了一份副本。

### 6.4 建议的修复（按优先级）

1. **短期**：安装 VS Build Tools 的 C++ 工作负载（需要管理员权限，我无法执行）

### ⚠️ 发布出去之后发现两个真实缺陷（0.2.1 带出）

在为项目补建测试安全网（覆盖率 89.2% → 100%，单测 254 → 319）的过程中，
暴露了两个**此前所有评估都没发现**的缺陷：

1. **空 env 时 `BuildEnvironmentBlock` 只产出 2 字节** → `CreateProcessW`
   返回 `ERROR_INVALID_PARAMETER(87)`，host 一旦传空 env，runner 完全无法启动 target。
2. **`IpcChannel.IsEndOfStream` 漏判 `ERROR_PIPE_NOT_CONNECTED(233)`**，
   对端以该码关闭时被误判为协议错误。

第一个尤其值得记下：当时那条单测**断言 2 字节**，而它的注释写着
「2 字节会让 CreateProcessW 返回 87」。注释与断言互相矛盾，
**测试反而把这个 bug 锁死了**。

这说明本报告「功能回归：通过」这个结论在当时是**真实但不充分**的：
7 个 C# 套件 139/139 全绿，仍然拦不住这两条路径 —— 因为测试没覆盖到它们。

已在 **0.2.2** 修复并发布（GitHub Release 含二进制）。
