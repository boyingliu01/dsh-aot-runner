# 开发环境

> 本文档描述在**一台新机器**上把这套开发环境跑起来需要什么、怎么验证、坏了怎么查。
> 目标是：任何人拿到仓库，30 分钟内能构建 + 跑通全部 A/B 验证。

---

## 一、工具链

| 组件 | 要求 | 本项目验证版本 | 用途 |
|---|---|---|---|
| .NET SDK | 8.0（含 NativeAOT 工作负载） | **8.0.427** | 构建 |
| ILCompiler 包 | 随 SDK 自动还原 | **8.0.33** | NativeAOT 编译 |
| MSVC 工具链 | VS 2022 Build Tools + C++ 工作负载 | **14.44.35207** | AOT 链接器（`link.exe`） |
| Windows SDK | 随 Build Tools 安装 | — | 原生编译所需头/库 |
| Node.js | ≥ 22 | **24.22.1** | 跑测试与基准 |
| DSH 安装 | 需含 `@deepseek-ai/dsh-subprocess-local` | **0.2.0-rc.2** | A/B 对照的基线 runner |

### 检查工具链

```bash
dotnet --version                      # 需 8.x
dotnet --list-sdks
ls ~/.nuget/packages/runtime.win-x64.microsoft.dotnet.ilcompiler/
node --version                        # 需 ≥ 22

# MSVC 是否装了 C++ 工作负载（AOT 必须有 link.exe）
"/c/Program Files (x86)/Microsoft Visual Studio/Installer/vswhere.exe" \
  -products '*' -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64 -property installationPath
```

最后一条有输出 = MSVC 可用。**没有返回值 = NativeAOT 无法链接**，需补装：
Visual Studio Build Tools 的「使用 C++ 的桌面开发」工作负载。

## 二、跑通验证（按顺序）

```bash
# 1. 质量门禁 —— 格式 + 静态检查 + JS 语法，约 15s
./build.sh --check

# 2. 构建
./build.sh

# 3. A/B 验证 —— 24 项，约 30s
npm test

# 4. 性能基准（可选）
node bench/d1-ab-bench.js
```

第 3 步全绿（`pass 24 / fail 0`）即表示环境就绪。

## 三、runner 路径解析

A/B 验证需要两个 runner：被测的 AOT 产物，和作为基线的 node runner。
两者都**不硬编码机器路径**，按下面顺序解析。

### AOT runner

| 顺序 | 来源 |
|---|---|
| 1 | `AOT_RUNNER` 环境变量 |
| 2 | 仓库内 `dist/dsh-aot-runner.exe` |

> ⚠️ 刻意**不**回退到 `%TEMP%` 之类的历史目录。早期版本会这样兜底，导致
> `dist/` 里没构建时测试静默拿一个**过期的旧二进制**去比对，结论看着全绿却毫无意义。
> 现在找不到就直接报错。

### node runner

| 顺序 | 来源 |
|---|---|
| 1 | `DSH_RUNNER` 环境变量 |
| 2 | `NODE_RUNNER` 环境变量（兼容别名） |
| 3 | 仓库内 `node_modules/@deepseek-ai/dsh-subprocess-local/lib/runner.js` |
| 4 | `DSH_HOME` 或 `%USERPROFILE%/.workbuddy/binaries/node/workspace` 下的同名路径 |

全部都找不到时，测试直接给出可操作的报错：

```
测试环境未就绪：

找不到 node runner（@deepseek-ai/dsh-subprocess-local/lib/runner.js）。
  A/B 验证需要它作为基线。可用 DSH_RUNNER=<绝对路径> 指定。
```

这是**环境问题**，与**行为不一致**是两回事 —— 前者会在测试开始前就失败，不会伪装成用例失败。

DSH 装在非常规位置时：

```bash
export DSH_RUNNER="D:/path/to/node_modules/@deepseek-ai/dsh-subprocess-local/lib/runner.js"
```

## 四、质量门禁

`./build.sh --check` 三道检查，任一失败即非零退出：

| 门禁 | 实现 | 失败时的修法 |
|---|---|---|
| C# 格式 | `dotnet format --verify-no-changes` | `dotnet format` 自动修复 |
| C# 静态检查 | 编译期 analyzer，`TreatWarningsAsErrors=true` | 按告警修改代码，**不允许用 `#pragma warning disable` 绕过** |
| JS 语法 | `node --check` | 修语法 |

静态检查是**0 警告硬约束**。引入严格 analyzer 时一次性暴露并修掉了 6 个真实问题，
包括 `ResumeThread` 返回值被忽略（失败时 target 永远挂起，外部表现为「调用卡住」）。

### 门禁自身可信吗

已做过正反例自校验：注入格式违规 → 退出码 1；注入 analyzer 告警 → 退出码 1；
恢复 → 退出码 0。**门禁本身也验证过会失败**，不是只会亮绿灯的摆设。

## 五、故障排查

### 构建期

| 现象 | 原因 | 处理 |
|---|---|---|
| `error MSB4025: An XML comment cannot contain '--'` | csproj 的 XML 注释里写了 `--` | 改注释措辞，XML 注释不允许连续两个减号 |
| `error NETSDK1047` / 找不到 ILCompiler | 无缓存且网络不可达 | 联网还原一次；或 `dotnet restore` 单独重试 |
| `LINK : fatal error LNK1181: 无法打开输入文件` | MSVC 未安装/未设置 | 装 Build Tools 的 C++ 工作负载 |
| 告警被当成错误 | 严格模式生效中 | 修代码，不要降低 `TreatWarningsAsErrors` |

### 运行期

| 现象 | 原因 | 处理 |
|---|---|---|
| `NtCreateDirectoryObject(\BaseNamedObjects\msys-2.0S5-...): 0xC0000022` | 产物目录是 Low IL | 跑 `./scripts/check-integrity.sh dist`，改用 `--out` 换 Medium IL 目录 |
| 写 `%TEMP%` 报 `Access is denied` 但 cmd/python 正常 | 同上，Low IL 跨完整性级别写入被拒 | 同上 |
| A/B 大量用例失败且 stdout 全空 | 产物被换成了旧版本 / 架构不匹配 | `./build.sh --clean` |
| `找不到 AOT runner` | 尚未构建，或 `dist/` 被清理 | `./build.sh` |

### 诊断开关

```bash
DSH_AOT_DEBUG=1 DSH_AOT_DEBUG_FILE="C:/temp/trace.log" ./dist/dsh-aot-runner.exe -- hostname
```

诊断信息**写文件**，不走 stderr —— stderr 已被 host 重定向用于转发 target 输出，
写进去会污染 A/B 比对且常常丢失。fd 1 是协议通道，更不能碰。

## 六、低完整性（Low IL）目录陷阱

**如果产物目录带 `Mandatory Label\Low Mandatory Level` 标签，从该目录启动的 exe 会继承
Low IL 并运行时崩溃。** 这是本项目踩过的最深的坑，完整背景见 README「重要陷阱」章节。

一句话版本：DSH 的 Windows 沙箱在 `workspace-write` 模式下会给工作目录打 Low IL 标签，
**且退出时有意保留**（源码注释：*"workspace ACEs stay standing as the reuse cache"*）。

```bash
./scripts/check-integrity.sh dist .    # 检查任意目录
```

`build.sh` 在构建前自动跑这项检查，命中即中止。
